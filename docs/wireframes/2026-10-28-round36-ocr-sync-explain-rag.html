§C · 乙 · 启动即增量同步（状态栏 / S7）

根因（已查证）：Patrol.poll() 每 scan_verify_minutes=30 分钟运行时间 才排一次全量对账（verify_every_polls = 1800s / 5s = 360 次轮询）。 应用不常驻 ⇒ 那个「30 分钟」永远走不到 ⇒ 六根 last_full_scan_at 停在 2026-10-16， 于是门禁 consistency 段每场都红在 C3 数据漂移（轮二十九 / 轮三十四 都是这个红）。 修法不动数据模型：AppContext.start_background() 之后立刻 jobs.enqueue("scan") 一条 —— 这条 job 类型、handler、去重分支（doc_id=NULL 同类只排一条）全都是现成的。

§D · 丁 · 库内问答（新屏 S9）

能做什么：向量已经全量建好（1,969,088 条 / 8,694 份），所以「拿我这一批书直接问问题」的 检索侧今天就是通的；缺的是把检索结果组织成用户能读的答案。 先定一件事：答案由谁生成 —— 这决定这一屏是「今天能做完」还是「要先装几个 GB 的模型」。
三问第一问：答案怎么来
甲 · 抽取式（不接模型）：答案 = 检索到的 N 段原文 + 文件名 + 页码，按相似度排序，不做任何生成。 零成本、零幻觉、离线、无新依赖。
乙 · 本地模型（Ollama / llama.cpp）：有真回答，但要你装数 GB 模型、占显存、单次几十秒。
丙 · 云端 API：质量最好最快，但需要 API key，且正文要发出去 —— 与 AGENTS.md「先定哪些数据只存本机」直接冲突，我不推荐。
我的建议是甲：先把「带页码引用的证据卡」做对，用户能自己读； 乙留一个可插的钩子（装了模型就多一段生成，没装就退化成甲）。
