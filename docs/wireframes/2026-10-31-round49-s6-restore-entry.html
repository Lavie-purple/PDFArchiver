§1 为什么这是个问题（把动线走一遍）

现状：想恢复一次备份，人要按的顺序是 —— 切到「恢复」标签页 → 按「选择备份文件」→ 在文件对话框里手工导航到 …\data\backups\backup-20261031-…-v8\ → 点其中的 catalog.db → 回到标签页确认"已选择"那句 → 按「恢复到新目录…」→ 再开目录对话框选一个空目录 → 等它跑完读回一句路径。两次对话框、两种模式（一次选文件一次选目录）， 而且第一个对话框根本不能直接选那个包。

  • "类型"列的意义：包与裸库能恢复回来的东西不一样（裸库只有 catalog.db， 向量文件回不来）。现在这个差别在界面上完全看不见，人点了裸库还以为恢复了整套。
  • "体积"列 + "选中内容"行：把"要准备多大空间"写在按之前，不写在报错里。 数字口径 = manifest.json 里的逐成员字节数（无清单 ⇒ 现 stat）； 单位换算只在显示层做，字节原值挂 tooltip。
  • 要跟着改的既有断言：tests/integration/test_ui_layout.py:97 test_选中备份文件之后恢复标签页也不许顶宽 现在靠 monkeypatch QFileDialog.getOpenFileName 走 page._select_backup()。 入口一换，这条要改成走"选中一行 + 填长路径标签"的同一条判据 （最低宽度 ≤ 可用宽、中段省略、tooltip 回读三件都不许丢），不是删掉。
  • 1024 档降级：五列表超过可用宽 ⇒ 按 D-040 既定口径整表横向滚动； 名称列走 Stretch、其余定宽一律进 set_table_columns （漏在口径外的列停在 Qt 默认值，守卫就看不见它们）。"选中内容"那行照 _elided 中段省略。不新增第三种降级形状。
  • 成本：一个新后端方法 + 一张表 + 一批断言。describe_backup() 读清单文件、 不碰 catalog.db，所以刷新列表不增加开库开销。

§7 绝对不做（防蔓延）

  • 不改「创建备份 / 备份到… / 刷新列表」三颗按钮的语义与位置（I121 ④ 的吸收行照旧）。
  • 不新增第四个标签页，不做"备份计划 / 自动保留"（那是 §二 的另一条，本轮不做）。
  • 不在界面里做恢复前 integrity_check 的进度条 —— 服务层同步跑、跑完只报结果； 恢复大库要多少秒没测过，所以本页不写任何耗时数字。
  • 不做"覆盖当前库"的选项（恢复必须写新数据根 —— 这条是 docs/DATABASE.md 六规定的 恢复流程，也是本轮 ISSUES I123 ② 的落点口径）。
  • 不改恢复落点布局（<根>\data\catalog.db 那套由 AppPaths 唯一算）。
  • 本页不带配色、图标、真实文案 —— 视觉由既有主题系统（src/pdfarchiver/ui/theme.py 的 QSS 令牌）在实现期管。
