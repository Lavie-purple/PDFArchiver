# 使用指南 —— 现在这个应用到底能怎么用

> 口径先说清楚：本指南只写**实测过**的用法。每一段「实测输出」都是这台机器上跑出来的原文，
> 不是示意、不是伪代码。凡是只能通过命令行用的能力，这里就写命令行，不假装界面上有按钮。
> 装在哪里、怎么装见 `docs/INSTALL.md`；OCR 单独有 `docs/OCR.md`；
> 备份与恢复见 `docs/BACKUP-RESTORE.md`；出问题见 `docs/TROUBLESHOOTING.md`。

## 一、一句话现状

| 你想做的事 | 今天能不能做 | 从哪里做 |
| --- | --- | --- |
| 启动应用、看这台机器的真实状态 | ✅ 能 | 双击 `PdfArchiver.exe`，默认落在「文档库」屏；运行状态与自检在「设置与状态」屏上半区（数字全是现算） |
| 扫描目录、抽正文、建全文索引 | ✅ 能 | 界面 S7「设置与状态」下半区点「添加目录…」选一个文件夹就登记好了（台账 **ISSUES I66** 已销账，2026-10-17）；要一次登记很多个目录见 §四 的命令行路子。根一旦登记，扫描/抽正文/建索引全自动 |
| 全文检索（文件名 / 路径 / 元数据 / 正文，带页码） | ✅ 能 | 界面 S1「文档库」顶部搜索框，支持四通道检索 |
| 分类树、多标签、把文档归进分类 / 打标 / 摘标 | ✅ 能 | S1 表格底下那一排「归入分类 / 加标签 / 移除标签」——**多选几行点一下，整批一次写库**（幂等：已在的不会重复加）；那句话逐字是仓储层回执。S8「分类与标签」管理增删改；界面 S1 左栏分类树筛选（**ISSUES I78** 甲，2026-10-19）|
| 把一组筛选条件存成智能集合 | ❌ 还不能 | 库里 `collections` 表没有界面入口写它，界面上那颗「存为智能集合」的按钮还不存在（**ISSUES I78** 乙）|
| 对扫描件跑本地 OCR | ✅ 单份点名 | S1 选中一行 →「送去识别」把**这一份**排进队列，表格底下那一行是回执（点名 / 该跑 / 新增任务，没排进去的写理由，后面跟着今日预算）；识别**不会自动排队**（D-028），S7 仍然只是 O1/O2/O3 三个读数。批量点名面板（**ISSUES I67** 乙）未落地，命令行路径见 `docs/OCR.md` |
| 在应用里读 PDF、翻页、跳页码、看阅读历史 | ✅ 能 | 界面 S2「PDF 阅读器」 |
| 按规则移动 / 改名 / 归档实体文件 | ✅ 能 | 界面 S3「归档预览与确认」：先点「生成预览」列出改名 / 移动方案（目标路径、路径长度、同盘 / 跨盘、被跳过的项与原因），在确认框里看过账才会提交后台执行；命名模板在这屏真的生效 |
| 重复检测 / 备份恢复 | ✅ 能 | 界面 S5「重复检测」按 SHA256 现算；S6「备份与恢复」用 `Connection.backup()` 快照 `catalog.db` |
| 撤销归档 | ✅ 能 | 界面 S4「操作日志」选中已完成的批次 →「整批撤销」，另开一条反向批次；撤不回的项（对面文件已不在、或原位被新占了）会被**排除并逐条写明原因** |
| 语义搜索 / AI 分类建议 | ⚠️ 要向量数据 | 界面 S1 可勾「语义搜索」、点「AI 推荐分类」；但**产品里还没有写向量的生产者**（**ISSUES I63** 丙 / 丁未做），没有向量时按钮显示"暂无向量数据"空态 |

**界面上只有两个按钮会真的改动你磁盘上的文件**：S3 的「执行归档」与 S4 的「整批撤销」。
两个都必须**先生成预览、再在确认框里看过那份账**（**D-042** 丙）：整批全部可逆时勾一次确认，
批次里含"回不去"的项时必须逐字输入确认词才算同意（**今天这一档还走不到**：默认的冲突处置是
**跳过**，所以任何一批的"不可逆"都是 0 条 —— 那句是条件句，不是你现在会遇到的分支，
**ISSUES I69**）。执行前还会查目标盘装不装得下，装不下时
「执行」直接**按不动**（不是"再提醒一次"）。搬每一份都先写日志，跨盘的先把目标复制出来、
逐项验完 sha256 才删源（G19），一项搬不成不会带走整批。
除此以外没有任何 UI 入口会移动、改名或删除文件。

## 二、启动与退出

```
PdfArchiver.exe                        # 双击或命令行，正常退出码 0
PdfArchiver.exe --data-dir D:\我的归档库   # 换数据根目录（搬家、多库、测试都用它）
PdfArchiver.exe --exit-after 20        # 起来 20 秒后自己关（冒烟验证用）
PdfArchiver.exe --version              # PdfArchiver 0.5.0
```

源码运行时把 `PdfArchiver.exe` 换成 `.venv\Scripts\python.exe -m pdfarchiver.app`。

- 退出码只有两个：`0` 正常，`2` 是启动失败（配置读不动 / 数据库打不开 / 后台起不来）。
  非 0 时崩溃堆栈一定落在 `<数据根>\logs\crash.log`，不是弹个框就完了。
- 关窗即干净退出：worker 线程停、watchdog 停、`state.log` 补一条关闭事件。
  任务没跑完就关窗不会丢 —— 下次启动会把中断的行回收重排（见 §七）。

## 三、界面：八屏导航

侧栏有 **9 项导航**（唯一来源是 `ui/nav.py` 的 `NAV_ITEMS`）。下表"屏"列是 **D-039** 的 8 屏编号 ——
一个屏可以挂多个入口，两套编号本就不同，所以别把"第几项"当成"第几屏"。默认落在**第 1 项「文档库」**
（记上次停留的页，则重启后回到那一页）。

| 侧栏项（`nav.py` 原文标题） | 屏 | 能做什么 |
| --- | --- | --- |
| 文档库 | S1 | 主工作区。左栏分类树筛选 + 中栏文档表 + 右栏命中面板；关键词 / 元数据 / 语义四通道检索都在这屏；选中一行 →「送去识别」把这一份排进 OCR 队列，回执落在表格底下那一行（**ISSUES I67** 甲，2026-10-19）；**多选几行** → 表格底下那排「归入分类 / 加标签 / 移除标签」就地展开目标清单，一次点击 = 一批文档一次写库，回执同样落在那一行（**ISSUES I78** 甲，2026-10-19）|
| 检索 | （并入 S1） | 这一项标着"未实现"，点开是说明页 —— 检索功能已在文档库屏，不重复做一屏 |
| PDF 阅读 | S2 | 打开库内 PDF，翻页、跳页码、阅读进度自动记录 |
| 归档预览与确认 | S3 | 填目标根目录 + 命名模板 → 勾选文档 →「生成预览」列出打算怎么搬（目标路径、路径长度、同盘 / 跨盘、被跳过的项与原因）→「执行归档」提交后台批次，界面只给回执「已提交 #N｜共 M 项」。**没看过计划时「执行」按不动**，预览之后又改了条件也按不动（台账 **ISSUES I55** 已销账，2026-10-17） |
| 操作日志 | S4 | 查看归档 / 索引 / OCR 等批次的历史与逐态读数；选中已完成的归档批次 →「整批撤销」开一条反向批次，撤不回的项排除并逐条写原因 |
| 重复检测 | S5 | 按 SHA256 现算内容相同的 PDF、显示浪费空间 |
| 设置与状态 | S7 | 上半区 = 运行状态与自检（版本、数据根、库统计、索引 / OCR / 队列进度、巡检读数，数字全是现算）；下半区 = 监测根列表（「添加目录…」真的登记、「移除选中」只撤监测）+ OCR 参数与三读数、模型状态 |
| 分类与标签 | S8 | 增删改分类树、管理标签；**右键**某一枝才有「改名… / 改父类… / 与…合并「X」 / 删除（先检查类下有无文件）」四项 —— 改父类与合并在这一屏只有这一个入口。「删除」按 §S8 定案**先查类下有无文件**：有则拒绝并列出文件清单（最多 12 行，多余的说「…还有更多」），空枝才走确认框（**ISSUES I78** 甲，2026-10-19）|
| 备份与恢复 | S6 | 用 `Connection.backup()` 快照 `catalog.db`、恢复到新目录、看迁移历史。**只备份库文件，不含 `settings.json` / 清单文件**（`docs/BACKUP-RESTORE.md` §八） |

**键盘快捷方式**：`Ctrl+F` 在文档库页聚焦搜索框并展开右栏命中面板。

**窄档降级**（窗口宽度 < 1024px）：右栏收成浮层（默认关），左栏收成 48px 条 + 分类按钮。

**状态页读数说明**：

- **每一个数字都是现算的**。页面里没有一个写死的数字；按下「重新读取数据库状态」就是重查一遍库。
  这个按钮存在的意义就是让"重启后数据还在"当场可验（见 §七）。
- `设置来源` 一行给出"内置默认值"还是"用户覆盖值 + 来源文件"，这是硬要求：
  你没写 `settings.json` 时它不会假装是你的选择。
- **改那九个键只能手改 `<数据根>\config\settings.json` 并重启**：`archive_default_template`／`archive_target_root`／`busy_timeout_ms`／`gpu_tasks_concurrent`／`log_keep_files`／`ocr_daily_page_budget`／`scan_poll_seconds`／`scan_verify_minutes`／`worker_threads`（现读 `config/settings.py` 的 `DEFAULTS`，九个，一个不多）。界面上**没有「保存设置」按钮**，写这个文件的函数 `config/settings.py:106 save()` **在产品里零调用点**（全仓只有 `tests/unit/test_settings.py` 引用它），文件也只在装配时读一次（`bootstrap.py:235`），没有热重载 —— 台账 **ISSUES I72**。
- **别把两个「设置」当成一个**：`config/settings.py::Settings` 读的就是上面那个 JSON 文件，**只读**；界面上的 `ctx.app_settings` 是 `db/repositories/settings.py::SettingsRepository`，写的是**库里的应用状态表**，主题偏好、上次阅读页码、会话状态都走它，重启不丢，与 JSON 文件无关。本项目对「设置」就这两个口径，各自存在哪、谁能写，以上两句为准。
- 状态页与启动路径**不跑任何同步库检查**（`integrity_check` / `quick_check` 的代价都与库大小同量级，
  2026-10-16 在 6.1GB 真语料库上实测：`integrity_check` 19 小时+未完、`quick_check` 冷/热缓存 452s / 478s，
  塞进启动路径会把应用冻死，见台账 **ISSUES I45**）。库健康核查的唯一入口是离线探针 `tests/probes/p12_consistency.py`
  （可自行限速，不在产品启动路径里跑）。

## 四、第一次扫描：注册监测根（界面 S7 一个按钮，或命令行批量）

界面路子（日常就够）：**S7「设置与状态」→ 下半区「监测目录」→ 点「添加目录…」**，在系统文件夹
选择器里挑一个目录，确认即登记 —— 库里立刻多一行 `enabled=1`，列表当场刷新，监听也当场挂上
（状态页的「监听根」数字随之 +1）。之后扫描 / 抽正文 / 建索引全自动，不用再碰命令行。

「移除选中」撤的是**监测**，不是你的文件：磁盘目录一个字节都不动，文档主记录与人工分类标注也
不删（重新添加就会接着扫）。所以恢复库之后要重新登记监测根，走的就是这颗按钮。
台账 **ISSUES I66**（2026-10-17 已销账）之前这两颗按钮是占位、且提示语把用户支去翻一个不存在
的配置键，当时的文档改动就是那一条的产物。

命令行路子只在**一次要登记很多个根**、或无人值守首扫时才需要（它写的是同一张 `monitored_roots`
表，效果与界面按钮完全相同）：

```python
from pathlib import Path
from pdfarchiver.services.bootstrap import bootstrap
from pdfarchiver.fs.identity import identity_key

ctx = bootstrap(Path(r"D:\归档库"))            # 数据根目录；不存在会自动建
corpus = Path(r"H:\文档")
ctx.roots.add(corpus.as_posix(), identity_key(corpus), label="我的工作文档")
for rep in ctx.scan.scan_all():
    print(rep.summarize())
queue = ctx.start_background()                 # worker 线程 + 文件监听 + 断点续扫
```

根一旦写进库，双击 `PdfArchiver.exe` 起来后就会自己扫这一根 —— 命令行只在做**批量登记**时才需要。

实测输出（273 份合成样本语料，这台机器）：

```
① 扫描： C:/Users/.../corpus：PDF 273｜新增 273｜改动 0｜改名 0｜未见 0｜未变 0｜排队索引 273（319 ms）
② 后台：worker 2 线程｜监听根 1 个
③ 队列排空耗时 2.4s｜任务状态 = {'done': 273}
④ 库： 结构版本 schema_version = 3 / 文档主记录 = 273（其中标记缺失 0） / 分类 = 14，标签 = 0 /
      监测根目录 = 1 / 任务 = done=273 / 应用内部状态条数 = 1
```

之后只要用同一个数据根启动应用，`roots` 表里那条根就会被自动监听 —— 也就是说
**注册一次，以后新增/改动文件不用管**（watchdog 增量 + 每 30 分钟一次周期校验，
`scan_verify_minutes` 可改）。

扫描阶段的口径（`ScanReport.summarize()` 的六个词，别混用）：

| 词 | 含义 | 判据 |
| --- | --- | --- |
| `新增` | 第一次见到的文件 | 路径与身份都是新的 |
| `改动` | 同一个文件内容变了 | 身份键相同、大小或 mtime 变了 |
| `改名` | 内容没变、路径变了 | 按 `(dev, inode)` 类身份识别，**不是按文件名** |
| `未见` | 库里记着但磁盘上找不到 | 标 `missing`，**不删库里的行，也不删磁盘文件** |
| `未变` | 什么都不用做 | 身份与路径都对得上 |
| `排队索引` | 本轮排进正文抽取队列的份数 | 不等于已经抽完，要看 `任务状态` |

## 五、检索：四个通道，口径写死在结果里

```python
from pdfarchiver.search.service import Criteria, FIELD_BODY, FIELD_FILENAME

r = ctx.search.search(Criteria(text="冷链物流",
                               in_fields=(FIELD_BODY, FIELD_FILENAME)))
print(r.channel_label, len(r.hits), r.matching_documents, r.took_ms)
for h in r.hits:
    print(h.field_label, h.page_no, h.snippet.line(), h.highlight())
```

实测输出：

```
trigram 短语检索（4 字）｜命中 5｜筛选内 273 份｜1ms｜各通道 {'filename': 1, 'body': 4}
   doc#1 第None页 文件名｜正文来源=native
     片段：冷链物流温度记录仪校准规程.pdf
     高亮区间：(0, 4)｜matched=True
   doc#1 第1页 正文｜正文来源=native
     片段：冷链物流温度记录仪校准规程，第 1 条要求 …
     高亮区间：(0, 4)｜matched=True
```

必须知道的几件事：

1. **口径只有一个名字**。`r.channel_label` 会明说这次是"trigram 短语检索（4 字）"还是
   "只检索文件名 / 路径 / 元数据（本次没有搜正文）"。中文查询词**少于 3 个字**时 trigram
   索引帮不上忙，会自动落到 `LIKE` 兜底通道，标签会跟着变 —— 不要按"结果条数"猜自己用了哪条通道。
2. **正文命中带真页码**（`h.page_no`）。文件名/路径/元数据通道没有页码，是 `None`，不是 0。
3. **高亮位置是 Python 侧算的**（SQLite 这个版本没有 `offsets()`）。当折叠规则不一致导致
   算不出位置时，`h.snippet.matched=False`、`h.highlight()` 返回 `None` —— 该行仍然出现在结果里，
   只是不高亮。程序不会编一个位置出来。
4. **正文来源分两种**：`native`（PDF 自带文字层）与 `ocr`（本地识别）。
   `h.body_source` 说的是这个，别把 OCR 文本当成原生正文引用。
5. 筛选条件全在 `Criteria` 里：`root_key` / `category_ids` / `tag_ids` / `tag_match_all` /
   `modified_from`+`modified_to`（**UTC unix 秒**，比的是文件修改时间）/ `fts_status` /
   `min_pages` / `min_size_bytes` / `include_missing` / `missing_only` / `sort` / `limit` / `offset`。
   分页是 `limit`+`offset`，**不存在"一次取全库"**。

## 六、分类与标签：界面 S8 能看能改，导出清单还没有

```python
c = ctx.catalog.add_category("合同审查", note="按需自建")
t = ctx.catalog.add_tag("待复核")
ctx.catalog.link_category(doc_id, c.id)          # 一份文档可以挂多个分类
ctx.catalog.link_tag(doc_id, t.id)
ctx.catalog.categories_of(doc_id); ctx.catalog.tags_of(doc_id)
```

实测输出（在数据根的一份临时副本上做的，副本已删）：

```
[写] 新建分类 id=15 name=合同审查｜标签 id=1 name=待复核｜样例文档 id=1 冷链物流温度记录仪校准规程.pdf
[写] link_category -> True | link_tag -> True
[写] categories_of = ['合同审查'] | tags_of = ['待复核']
[写后查] 浏览模式（未输入查询词，排序 relevance）｜命中 1｜符合筛选 1 份
[写后查] 按标签筛 → 符合筛选 1 份｜命中 1
[树] 层级示例（缩进=深度）：
   合同审查 (id=15, parent=None)
   文档类型 (id=7, parent=None)
     产品手册 (id=12, parent=7)
     技术文档 (id=11, parent=7)
     标准规范 (id=14, parent=7)
     白皮书 (id=13, parent=7)
```

- 首次建库会种下 **14 个**默认分类（两层），这是实测数字，改默认模板要走迁移，不是改常量。
- `origin` / `confirmed` 两个参数是给"AI 建议分类"预留的口径（阶段 6）：机器给的一律
  `origin="ai", confirmed=0`（措辞取自 `db/repositories/catalog.py:214`），人工确认后才有 `confirmed=1`。
  今天产品里**没有任何调用方写 `origin="ai"`** —— `semantic/classify_service.py` 只出建议、不落库，
  所以现在库里全是手工，全是 1。
- **导出分类与标签清单**是阶段 3 第 10 项，未实现。想现在拿清单只能自己查 `categories` / `tags` 两张表。

## 七、重启之后东西还在吗 —— 自己验一遍

1. 启动应用，记下「文档主记录 = N」「任务 = done=…」「监测根上次全量对账」那几行。
2. 关窗口（正常关闭，别用任务管理器杀）。
3. 再启动，按「重新读取数据库状态」。

判据：**数字一致，且 `logs/crash.log` 不存在**。冻结产物的实测就是这样走的 —— 干净目录首启、
扫描 273/273、正文入库、关窗、再起，二次启动读数与一次启动相同，`integrity_check = ok`。

非正常关闭（杀进程 / 断电）也要能恢复：启动时 `WorkQueue.recover()` 把上次停在 `running`
的行重新排队，`state.log` 里 `background.started` 事件带 `recovered` 与 `resume_index` 两个数字。
杀进程实测：重启后 `recovered` 非 0，任务最终全部 `done`，没有一行卡在 `running`。

## 八、日志：出问题先看这三个文件

| 文件 | 内容 | 什么时候看 |
| --- | --- | --- |
| `<数据根>\logs\app.log` | 轮转运行日志（2MB × `log_keep_files`=5） | 想知道扫描/索引/OCR 每一步发生了什么 |
| `<数据根>\logs\state.log` | 一行一条 JSON 的生命周期事件（启动、迁移、后台启动、关闭、失败） | 事后对账"它到底起来了没有、什么时候关的" |
| `<数据根>\logs\crash.log` | 未捕获异常与线程内异常，含完整 traceback，追加不轮转 | 只要它存在就是有故障；退出码 2 必读 |

时间戳一律 UTC 带 `Z` 后缀，不用本地时区 —— 远程帮人诊断时不用猜对方在哪个时区。

关键事件行（`state.log`）的正常序列：

```
startup.begin → migration.applied → startup.done → background.started → window.ready
```

`window.ready` 里的 `cold_start_seconds` 就是界面上那行冷启动读数；阈值 1.5s 是**约定值**，
不是实测保证 —— 满载机器上实测到过 3.129s（`docs/ISSUES.md` ISSUES I25）。

## 九、性能与量级的真实边界

- 冷启动：源码空载 **0.428–0.77s**（交付链那一场现场打印 **0.437s**，G1 阈值 1.5s **[约定]**），
  满载（CPU 96.5%）**2.99–3.13s**；**冻结产物 1.109s** —— 比源码慢 2.5 倍，这是打包带来的真实代价。
  G1/G2 是负载绑定读数，必须连着门禁第一行的负载一起比。
- 扫描：**真实语料已量过**。6 个监测根扫得 **10,977 份 PDF / 31.3 分钟**，扫描失败 26 条全是系统目录的
  `PermissionError`（命中排除逻辑），逐根读数在 `docs/VERIFICATION.md` §4.14。
  273 份合成样本那组（全量对账 **319–332ms**）只是小库对照。
- 检索：**G2（搜索 P95 ≤ 500ms）已在真实量级实测并判 GREEN** —— 库内 `text_pages`
  **1,972,578 行**、20 条查询 × 5 次 = 100 个计时样本，**P50 135ms / P95 328ms / P99 332ms**
  （`docs/VERIFICATION.md` §4.16）。第一次跑同一条判据是 **P95 2,809ms 判 RED**，
  降到 328ms 靠的是正文 LIKE 通道带上 60,000 行扫描预算（**D-051**），
  **代价是召回**：那条 `'发票'` 查询的命中行数从 200 降到 169，其余 19 条一行没变。
  这组读数绑真库、绑负载，不会自己复跑 —— 入口是 `scripts/g2_search_benchmark.py`。
- 归档搬运：单份文件在同盘是 `shutil.move`，跨盘是 copy + 验 sha256 + 删源，
  **没有任何按量级反算过的红线**（G4 全量哈希 ≤1h 只在首扫那一场实质达成过，不是归档批次的实测）。
  界面上一次提交几十份是当场能等的量，一次提交几千份需要你自己留出时间，且中途关窗会由
  `recover()` 重排（见 §七）。
- OCR：单页 **1,985–3,379ms**（DML 加速，负载影响明显），日预算默认 6,000 页，见 `docs/OCR.md`。
- 库文件：真实语料首扫后 `catalog.db` 实测 **6.1GB**（`%LOCALAPPDATA%\PdfArchiver\data\catalog.db`，
  出处 §4.14）。冻结冒烟那场的 273 份 / 544 页正文 → **864,256 字节**（≈844KiB）是小库对照，
  出处在 `docs/BACKUP-RESTORE.md` 二。
