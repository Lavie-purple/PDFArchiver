## 阶段 2 · 文件扫描与索引

**做**：`fs/scanner` + `fs/identity` + `parsing/pdf` + `indexing/fts` + `jobs` 队列。
**准入门槛**：Q1、Q2、Q4 已答。

| 门禁 | 内容 | 实测依据 |
| --- | --- | --- |
| G3 | 首建全量索引 ≤ 6h | p2 中位 147.9 页/s × 202 万页 = 3.80h |
| G5 | 单页 150dpi 渲染 ≤ 400ms | p2 实测中位 135.1ms |
| G6 | 禁止全量预渲染（断言拦死） | 202 万页 = 75.9h / 缓存约 1.7TB |

| G10 | FTS 幽灵行数 = 0 | p1 证明漏列**不报错**，只能靠这条断言发现 |
| 新 | 重叠监测根不产生重复主记录 | p7：3 条不膨胀 |

**做**：`search` 编排 + 分类/标签/智能集合 + 阅读器屏。
**准入门槛**：Q1、Q7（搜索屏与阅读器屏线框已确认）。

| 门禁 | 内容 |
| --- | --- |
| G2 | 搜索 P95 ≤ 500ms（基线）；**短查询 LIKE 回退不得静默变 0 结果** |
| G11 | 300 文件批量事件丢失 = 0 |
| G12 | 监测根被改名后 ≤ 60s 自愈 **[约定]** |

**SPEC 原文偏离**：SPEC 把 OCR 放在阶段 5，但**扫描页在阶段 3 就会大量出现**（p2 抽样 37.5% 是纯扫描件）。
所以阶段 3 必须先把「疑似扫描件」标记出来并显示"未检索正文"，否则用户会以为搜索没坏就是没内容。

## 阶段 4 · 安全归档、重复检测与备份

**做**：`fileops`（plan/preview/journal/execute/undo）+ 重复检测 + `backup`。
**最高风险阶段** —— 唯一会改用户磁盘的阶段。

| 门禁 | 内容 |
| --- | --- |
| G4 | 全量哈希 ≤ 1h（实测 9–39min） |
| G17 | 杀进程重启后 journal 每条状态都能被恢复矩阵归类，未知状态 = 0 |
| G18 | 归档→撤销后：源存在、字节一致、sha256 一致、目标已消失 |
| G19 | 跨盘移动**绝不先删源**：注入"删源前崩溃"证明它真的没删 |
| 新 | 预览与实际执行的文件集合**逐条一致**（先算 sha256 集合差，非 0 即中止） |
| 新 | DB 事务回滚**不等于**磁盘回滚 —— 断言存在一条测试专门验这点 |

## 阶段 5 · OCR

**准入门槛**：**Q3 必须先答**。按 p5 实测，SPEC 原文的"对扫描件建立 OCR 索引"在全量口径下
是 1,144 GPU 小时 = 8h/天 × **143 个工作日**，做不了。

| 门禁 | 内容 |
| --- | --- |
| G13 | 单页耗时预算 284ms（A-OCR-1 反算）—— **当前实测 3,281ms，判 RED**。选 3（限额后台）则改为"每日预算跑满即停且进度可见"，G13 作废重定 |
| 新 | CPU 后端在**无 GPU 机器**上能独立完成同一批 OCR（结果与 DirectML 逐字一致，p5 已验 `text_identical`） |
| 新 | OCR 文本进 FTS 后 `source_kind='ocr'` 可筛选、可整批删除且不留幽灵行 |
| 新 | OCR 结果按 **B 档**纳入备份（804–1680h→实测 1,144h，事实上不可再生，docs/02 一） |
