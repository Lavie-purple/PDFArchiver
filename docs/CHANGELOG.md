### F1 · 单行不换行的长路径把窗口顶宽，并**永久**榨瘪侧栏（台账 **ISSUES I47**，CLOSED）

### F2 · 八张表的列宽没有口径（台账 **ISSUES I48**，CLOSED）

- **症状**：八张表原先都只写一句 `setStretchLastSection(True)` —— Qt 于是把除最后一列以外的所有列

- **两条我自己踩过的实测纠正**（都写进了 `table_layout.py` 的 docstring，免得下一个人重犯）：
  ① **吸收列不能落在内容列上**：定宽列已经把视口吃满时，`Stretch` 那一列被压成一条缝（实测 25–38px），
  而且**永远是这一条缝** —— 归档页原先把吸收列放在「文件名」上，窗口压窄时牺牲的恰好是用户唯一要读的那列；

  专门做隔离实测才发现 **Qt 的横向滚动范围按"档"不按像素** —— `maximum()==2` 时把值拧到底，第 0 列被推出
  `−296px`、末列进视口。滚动一直是好的，所以"全定宽 + 横向滚动"这条修法站得住，但理由要换一个。

  点名 25px；`setHorizontalScrollBarPolicy(ScrollBarAlwaysOff)` → 点名「可见=False」。
- **两条注入抓出来的是守卫自己的假绿**（不修它就等于白写）：① 一次 `processEvents()` 之后 `Stretch` 列留着

  **一级一级压**；加了 `_settle()` + 步进之后那条注入才红。② `maximum() >= 1` 在滚动条被禁用的情况下照样绿，

### 改方向（被证据推翻的原计划）

- **OCR 从"索引的自动步骤"改为"用户显式触发"**：全量 101 万页需 1,144 GPU 小时（8h/天 × 143 工作日），
  而按无人值守窗口反算的预算是 284ms/页，实测 3,281ms。p5 **保持 RED**，没有调阈值凑绿。
- **量化不作为提速手段**：int8 在 DirectML 上 79.3 chunks/s，比 fp32 的 146.9 **慢 1.85×**。
- **新增一条产品级未决项**：全文索引体积外推 28–48GB（×10 档 280–480GB 不可行）→ 需选全量/子集/降密度。
