阶段 0 建立，之后**每次改代码都要同步维护**。文件名用你指定的工程文档口径，正文用中文。

| 文件 | 用途 | 什么时候必须改它 |
| --- | --- | --- |
| `PROJECT_SPEC.md`（仓库根） | 产品需求与**不可突破的边界** | 功能范围、边界、硬件前提变化时 |

| `TESTING.md` | 测试方法、测试命令与验收标准 | 新增门禁、改阈值、加测试层时 |
| `DECISIONS.md` | 重要技术决策、理由和替代方案 | 做一个会影响多个模块的选择时 |

`gates/final.py` 的 `guards` 段里有一条断言在钉这件事（四份都在场 + 每份都引用当次实测读数 +

## 维护约定

1. **数字不许只写结论**：任何耗时/体积/吞吐/量级数字都要在 `VERIFICATION.md` 或 `CHANGELOG.md` 有实测出处，
   写清楚是哪个探针、哪个产物 JSON。没有出处的数字标 **[推算]** 或 **[约定]**。
2. **决策不许散落在代码注释里**：影响多个模块的选择一律进 `DECISIONS.md`，含替代方案与被否原因。
   `DECISIONS.md` 是决策的**唯一登记处**（编号 `D-0NN`）；`ARCHITECTURE.md` 五 那张表只是架构视角的视图，
   第一列直接引用登记号，**不自行编号** —— 同一件事两套号，早晚对不上。
3. **删文件先删引用**：本文档与代码里的路径引用一起改，不许留死链。
4. **每次收尾过一遍**：全量回归 → 埋点/文档更新 → 已知问题逐条销账 → 临时文件清零。
5. **阶段 1 起，第 4 条的机器判据是一条命令**：`python gates/stage1.py` 末行必须打印 `VERDICT: ALL GREEN`；
   阶段 2 起改跑 `python gates/stage2.py`（在 stage1 之上加「后台生命周期」与「e2e 真链路验收 + 真实检索结果」两步）；
   **阶段 5 起改跑 `python gates/stage5.py`**（再加三步：产品路径端到端实测、每日页预算真停机、真引擎套件不许退化成 skip；
   空载实测一条命令 **382s**，含两条反向注入 46/46 + 45/45）。
   **跑之前看负载**：门禁起跑第一行打印 `起跑负载：CPU x%｜可用内存 xMiB｜…`，
   G1/G2 的冷启动阈值是负载绑定读数，机器不空闲时那两行必红 —— 空载重跑，**不许放宽阈值**（ISSUES I25）。
   它串起依赖守卫 → 架构守卫 → 全量回归 → 冷启动实测 → 反向注入；不绿就不算收尾，也不许开下一阶段。
   阶段 N 门禁脚本就叫 `gates/stageN.py`，阈值只在脚本里出现一处；阶段 7 才拆成 `01..09` 串行链（R-007）。
   想快一点：`--quick` 只跑阶段 5 三行，`--no-injection` 跳过两条注入探针（141s）—— **收尾必须跑全链，不跑快链**。
6. **最终交付不是 `gates/stage5.py`，是 `gates/final.py`**：它按段编排（九段，每段仍是**它自己那份门禁/探针里的断言**，
   这里不新增判定口径），默认只跑快的那几段，慢段（`injection` / `ocr` / `soak` / `package`）要 `--only` 点名或 `--all`。
   凡被 `--only` 跳过的段，输出里明写"本次未跑"，**不许把一场的"全绿"读成整个项目的"全绿"**。
   交付文档在场性（四份用户文档 + 报告五分栏 + 无占位符 + 引用当次实测）是这条链里的 `guards` 段。
7. **引用也是断言**：文档与代码里凡指向"某台账编号 / 某条测试 / 某个文件路径"，收尾必须逐条 grep 确认它存在，
   并且它说的就是这件事。本轮实际抓到三类空指：不存在的测试名（ISSUES I28）、不存在的台账编号（ISSUES I34）、
   指向 gitignored 且收尾会删掉的 `.probe_work/scratch_*.py` 的出处（ISSUES I33/ISSUES I34）。
   证据只能指向**入库且长期存在**的东西：探针、门禁、台账条目、`docs/VERIFICATION.md` 的节号。
   **但"grep 得到"不等于"指对了"** —— `I<n>` 这个字形在本项目有三本账（台账 `docs/ISSUES.md` 的行号、
   `docs/TESTING.md` 四 的 p9 坏法 ISSUES I1–ISSUES I46、p10 坏法在代码里是裸数字 `Case("39", …)` 而文档写成 `ISSUES I39`），
   所以裸写 `ISSUES I39` 两种读法都能找到东西，却只有一个是对的（规模与销账条件见 **ISSUES I35**，OPEN）。
   **同一条还管计数**：文档里凡"多少处 / 多少条 / 多少行"这类会随每一轮增长的数，**必须同时写明时点与数法**，
   并说明"后续引用必须重测"。本轮的活案例：`docs/ISSUES.md` 那组 **509 / 56 / 453** 是**交付轮定稿那一刻**的快照，
   而线框轮收尾现数是 **664 / 89 / 575**（2026-10-15 13:24，同两条正则）—— 把 453 读成"现在还剩这么多"就是误报。
   从现在起新写入**一律带命名空间**：`ISSUES I<n>` / `p9 注入 I<n>` / `p10 注入 #<n>`，不许再裸写。
   存量的 **453 处裸写**本轮**没有**改写 —— 跨 8 份历史阶段文档的批量改写在收尾做，风险是改错而不是改净。

   `docs/ROADMAP.md` 阶段 0 的 `Q1..Q8` 是本项目**唯一**的"待你拍板"编号，任何对外决策清单引用它必须写成
   `ROADMAP Q5`；我自己临时列的选项一律用 **甲/乙/丙** 或 `S1/S2`，**不再另起一套 `Qn`**。
