# 备份与恢复说明

> 先说结论：**备份/恢复有界面了（S6），但它只做两件事** —— 用 `sqlite3.Connection.backup()`
> 把 `catalog.db` 拷一份出来、以及把某个备份灌进一个**新目录**（绝不覆盖当前库）。
> 界面不会把 `settings.json`、分类标签、OCR 文本打包成一个"备份包"，也不做恢复前校验 ——
> 那些仍在下面 §三/§四 的手工流程里。**迁移前自动快照**照旧在跑（每次结构升级前生成）。
> 本文写的是"S6 界面能做什么"+"界面没覆盖的怎么手工补"，全部步骤都在本机实测过。
>
> 备份对象口径不变：`catalog.db` 里**含**人工分类标签与 OCR 正文（B 档，不可轻易再生），
> 所以只要备份了这个库，就保住了最难重建的东西。

## 一、先分清四类数据：丢了能不能再生

口径来自 `docs/DATABASE.md` 一（同一张表，不另写一套）：

| 档 | 内容 | 丢了会怎样 | 谁负责备份 |
| --- | --- | --- | --- |
| **A 不可再生** | 你磁盘上的 PDF 本体 | 真损失，无法恢复 | **本程序不备份用户 PDF**，只登记它们在哪 |
| **B 难再生** | `catalog.db` 里的人工成果：分类、标签、集合、归档映射、**OCR 正文** | 要重做人工标注；OCR 要重烧 GPU | 必须进备份包 |
| **C 可再生** | 全文索引花名册、原生正文 `text_pages(source_kind='native')`、**语义向量文件 `data\vectors.npy`** | 重扫 / 重跑嵌入即可 | 界面按钮现在也一起拷（见下面那段） |
| **D 纯缓存** | `data\cache\`、缩略图 | 无所谓 | 不备份 |

**为什么向量文件明明可再生，却要进备份包**（**ISSUES I123** ①，2026-10-31 起）：
它不在 `catalog.db` 里，是 `data\vectors.npy` 这个独立文件，而**库里 `vector_meta` 记着"我有多少条向量"**。
包里没有它 ⇒ 恢复出来的根一打开，语义搜索当场报「`vectors.npy` 只有 N 行，而 `vector_meta` 报到第 M 行」，
界面上写的却是"恢复成功" —— 缺的东西要等到有人用语义搜索才暴露。重跑嵌入确实能补回来
（按实测吞吐是真能等的量级），但那是一次**全库重烧**，比拷一个文件贵得多。
所以这一档的口径是：**能再生 ⇒ 不作为"丢了就完了"的 B 档，但备份时顺手带上**。
重跑嵌入的实测代价：真库全量 **1,966,435 页 = 450.4 分（7 小时 30 分）@ 72.77 页/秒**
（2026-10-26 轮二十六 ⑤，`docs/VERIFICATION-RUNLOGS-ARCHIVE-3.md`），而把它拷进备份包只是
拷一个 ≈1 GiB 的文件（那次跑完落盘的 `vectors.npy` 是 1,073,741,952 B）。

**为什么 OCR 文本按 B 档而不是 C 档**（这条最容易搞错，所以写进正文）：
本机 DirectML 实测单页 **1,985–3,379ms**（负载相关），按每日 6,000 页预算反算，
全库待 OCR **1,014,112 页 ≈ 169 天**。所以"重扫就能恢复"这句话**对原生正文成立、对 OCR 正文不成立**。
实测证据见 §四 第 2 步：恢复快照后重扫 273 份，正文回到 **543 行**，而备份前是 **544 行** ——
差的那一行就是唯一那页 OCR 文本，重扫不会把它找回来（OCR 只处理你显式点名的页，D-028）。

## 二、备份从哪来：S6 界面按钮 + 迁移前自动快照

现在有**两个来源**：

1. **S6「备份与恢复」页的「创建备份」按钮** —— 见 §三·甲，产出一个目录包
   `backup-时间戳-v版本\`（内含 `catalog.db` + `vectors.npy` + `settings.json` + `manifest.json`）。
   2026-10-31 之前的老产物是单个 `catalog-时间戳-v版本.db`，仍然可读（**ISSUES I123**）。
2. **每次结构迁移前的自动快照** —— 见下面「生成时机与位置」，产出 `pre-migration-*.db`。

### 迁移前自动快照 · 生成时机与位置

每次启动时若 `schema_version` 落后于 `src/pdfarchiver/db/migrations/` 里的最新编号，
**在动结构之前**用 `sqlite3.Connection.backup()` 存一份完整副本：

```
<数据根>\data\backups\pre-migration-<四位迁移序号>-<本地时间戳>.db
```

- 快照失败或迁移失败 → 异常里带着快照路径（`MigrationError.snapshot`），迁移在单事务里回滚，
  库停在原版本，不会留下"改了一半"的结构。
- 没有增量迁移的启动**不会**产生快照 —— 所以"backups 目录是空的"是正常状态，不等于坏了。
- 快照**不轮转、不自动删**（数量上限 = 迁移条数）。**保留策略（2026-10-21 定）**：每次迁移收尾只留**最新 1 份**大快照，更早的逐份确认「能打开＋`schema_version` 读得动」后手动删除 —— 产品不会自动清理，这一步在收尾清单里手工做。
- 2026-10-21 实测：真数据根原有 **8 份 ≈22.3GiB**（0001–0006 是空库历史共 740KiB；0007 **v6 / 10,980 条**、0008 **v7 / 10,977 条**），按此策略删到 **1 份**（`pre-migration-0008-20261020T122144.db` **11,967,422,464B ≈11.15GiB**，删后复核仍能打开、v7 / 10,977 条）；主库＋备份 **≈33.4GiB → ≈22.3GiB**，C 盘可用 **203G → 215G**。

### 实测清单（冻结产物冒烟留下的现场，273 份文档）

```
  绿  C11  最新快照整库体检，其余快照开库读版本
        快照 3 份｜pre-migration-0001-20261015T032946.db 8KiB@v0 ｜
        pre-migration-0002-20261015T032946.db 120KiB@v1 ｜
        pre-migration-0003-20261015T032947.db 148KiB@v2
```

`@v0/@v1/@v2` 是**这份快照当时库里停的结构版本**，也就是"恢复到它 = 退回到那次迁移之前"。
第一份 8KiB 是空库（建库前的原始状态），所以它连 `schema_version` 表都还没有。

### 谁算「一份快照」—— 唯一口径（2026-10-31 起，**ISSUES I123**）

`snapshot_paths()` 与 `snapshot_label()`（都在 `src/pdfarchiver/services/backup_service.py`）是**唯一**
回答「`data\backups\` 里哪些文件算一份库快照」的地方，三个消费者一律 import 它，不许再各写一遍 glob：
产品 S7 库体检的 C11（`services/db_check.py`）、真根核查工具的 C11（`tests/probes/p12_consistency.py`）、
反向注入探针挑受害者（`tests/probes/p12_inject.py`）。两种形状都认：

- 顶层裸 `.db` —— 迁移落的 `pre-migration-*.db`，以及 2026-10-31 之前 S6 产的单文件备份；
- 目录包里的 `catalog.db` —— `backup-*\catalog.db`。

包里的库在报告里印成 `backup-20261031-…-v8/catalog.db`（**带包名**），否则每个包都印成同一个
`catalog.db`，读数分不出是哪一份。

⚠️ **一条连带成本**（改这个口径的理由就在这条）：那个 glob 从前只看得见顶层裸 `.db`，所以 ①甲 之后
**你刚创建的那个备份包不会进 C11 的名单** —— 「整库体检最新一份」体检查的还是迁移时的旧快照，
读数照绿，而真包一次都没被人打开过。现在最新一份通常是当天那个包里的 **12.1 GB** 库，
C11 的整库体检就落在它身上（该项历史实测 **571–1,156 秒**，逐场读数见 `docs/VERIFICATION-RUNLOGS*.md`）。
核查工具那档 `--c11-deep`（全部快照逐份整库体检）成本按包数线性涨 ⇒ 每多点一次「创建备份」
就多一份 12.1 GB 的快照，上面那条「每次迁移收尾只留最新 1 份」的保留策略因此更得手工做。

## 三、备份：界面按钮（甲）与手工（A/B）

关键约束：库跑在 WAL 模式下（`PRAGMA journal_mode=WAL`），**应用运行中直接复制 `catalog.db`
会备到不一致状态** —— 已提交的数据可能还在 `catalog.db-wal` 里没落回主文件。这条写进
`docs/DATABASE.md` 六，不是建议，是必须。所以下面三种做法都绕开了"运行中拷文件"。

### 做法 甲：S6 界面的「创建备份」按钮（推荐）

侧栏进「备份与恢复」→ 第一个标签「备份」→ 二选一：

- **「创建备份」**：把当前库连同语义向量库、设置一起备到 `data\backups\`，产物是一个**目录**
  `backup-YYYYMMDD-HHMMSS-v结构版本\`，成功弹窗给出完整路径。
- **「备份到...」**：同上，但目标目录由你选。

按钮可以在应用运行时点（库走的是 Backup API，不拷文件，所以一致）。目录里固定这几样
（**ISSUES I123** ①，2026-10-31 起）：

| 成员 | 怎么来的 | 不在场会怎样 |
| --- | --- | --- |
| `catalog.db` | `sqlite3.Connection.backup()` 一致性快照 | 按钮直接失败 |
| `vectors.npy` | 原样拷贝 —— **建过语义索引才拷**，没建过就不是成员 | 恢复出来的根里库说有向量、文件却不在，语义搜索当场报「向量文件行数盖不住 `vector_meta`」，而界面写着"恢复成功" |
| `settings.json` | 原样拷贝，文件不存在就不拷 | 设置退回默认值 |
| `manifest.json` | **最后一步**才写，逐成员记名字与字节数 | 这次备份根本没做完（半成品会被整个撤掉） |

两条口径值得知道：**先快照库、再拷向量文件**（反过来会备出"向量下标比文件行数还大"的一对文件，
恢复完一搜就炸）；**清单最后写**（中途任何一步坏掉 —— 磁盘满、文件读不动 —— 都把整个目录撤掉，
不留一个看着像备份的东西）。恢复时逐个按清单核对字节数，再跑一遍 `PRAGMA integrity_check`，
对不上就拒绝并删干净已经写出去的文件。

改造前的产物仍然可读：单个 `catalog-*.db` 文件、以及没有 `manifest.json` 的老目录包。

### 做法 A：复制整个 `data\` 目录（要把 journal 台账、整目录一次搬走时用）

1. **完全退出应用**（关窗口，不是最小化）。
2. 确认 `<数据根>\data\` 里没有 `catalog.db-wal` / `catalog.db-shm`。
   正常关闭会做 checkpoint 并删掉这两个文件；**如果它们还在，说明还有进程连着这个库，别拷**。
3. 把 `<数据根>\data\catalog.db`、`<数据根>\data\vectors.npy` 与 `config\settings.json` 一起复制到备份位置。
   `cache\` 不用拷（D 档）；`backups\` 里的快照建议一起拷。
   整目录拷最大的好处是把 `data\journal\` 的归档台账一起带走（§六 最后一条）。

实测：正常关闭后 `data\` 目录里只剩 `catalog.db`（864,256 字节，273 份文档 / 544 页正文），
`-wal`/`-shm` 不残留。
> 追注（2026-10-31）：这句是**阶段 6 之前**的读数，那时 `data\` 里确实只有库一个文件。
> 现在建过语义索引的库会多出 `vectors.npy`，"只剩 catalog.db"不再是应有的形状 ——
> 检查的对象改成「不许有 `-wal` / `-shm`」，别的文件都该跟着拷走。

### 做法 B：用 SQLite 的 Backup API（应用可能在跑时用这个）

```python
import sqlite3
from pathlib import Path

root = Path(r"D:\归档库")                      # 你的数据根
out  = root / "manual-backup.db"               # 备份目标；不要写进 data\backups\，那是快照目录
src = sqlite3.connect(root / "data" / "catalog.db")
dst = sqlite3.connect(out)
src.backup(dst)                                # 一致性快照，可以在应用运行时做
dst.close(); src.close()
print(out.stat().st_size, sqlite3.connect(out).execute("pragma integrity_check").fetchone()[0])
```

`src.backup()` 读到的是一致视图，不需要停应用。这就是产品内部用的同一个机制。

**备份要包含 OCR 文本**：OCR 正文就在 `catalog.db` 的 `text_pages(source_kind='ocr')` 里，
所以只要备份了 `catalog.db` 就等于备份了它。**不要**只备一份"重建脚本"就认为能恢复 —— 169 天。

## 四、恢复

**核心安全约束：本程序不提供任何"自动覆盖当前库"的路径** —— 无论界面还是脚本。
S6 的恢复按钮只把备份灌进一个**新目录**，然后提示你重启应用指向新库；下面 §四·手工 的
`src.backup(dst)` 也只是把某份快照恢复到指定库文件，要你亲手选源和目标。

### 方式 甲：S6 界面的「恢复到新目录」按钮

侧栏「备份与恢复」→ 第二个标签「恢复」：

1. **「选择备份文件」** → 选一份备份。这个对话框只能选**文件**，所以两种产物走法不同：
   - 老产物（单个 `catalog-*.db`、`pre-migration-*.db`）直接选它；
   - 新格式的**目录包**：进到那个 `backup-*\` 目录里选 `catalog.db`。程序看见它旁边有
     `manifest.json` 就按**整包**恢复（向量文件、设置一起回来），不会只回半个库（**ISSUES I123**）。
     「在备份列表里选中一行 → 点恢复选中项」那个形状还没做，等线框确认（见 §八）。
2. **「恢复到新目录...」** → 选一个**空目录**，它就是恢复出来的新数据根。程序按 `AppPaths` 的布局落盘：
   `那个目录\data\catalog.db` + `data\vectors.npy` + `config\settings.json` —— 应用启动时读的正是这套。
   目标里已经有 `data\catalog.db` 的话**当场拒绝**，一个字都不写。
3. 弹窗明确告诉你：**"当前应用仍在使用旧库。要使用新库，请重启应用并指定新数据目录。"**
   即用 `PdfArchiver.exe --data-dir <那个新目录>` 重启 —— 传的是**数据根**，不是库文件。

界面恢复**已经做**：按 `manifest.json` 逐个核对字节数（少一个字节就拒绝）、恢复完跑
`PRAGMA integrity_check`、任一步失败把已经写出去的文件删干净（半个库比没有库更坏）。
界面恢复**还不做**：路径重新对账 —— 恢复完请照 §五 跑一致性探针。

### 方式 乙：手工脚本（要精确挑某一份快照、或想在原目录内换库时用）

⚠️ 下面脚本会把某份快照灌回 `catalog.db`，**等于覆盖那个库**，所以第 0 步先保住现状。

```python
import shutil, sqlite3
from pathlib import Path
root = Path(r"D:\归档库")
cur = root / "data" / "catalog.db"
shutil.copy2(cur, root / "before-restore.db")           # 万一恢复错了还能回来
s = sqlite3.connect(cur); print("现状：", s.execute("select count(*) from documents").fetchone()[0], "份文档")
s.close()
```

### 第 1 步：把快照灌回 `catalog.db`

```python
import sqlite3
from pathlib import Path
root = Path(r"D:\归档库")
snap = root / "data" / "backups" / "pre-migration-0002-20261015T032946.db"
dst  = root / "data" / "catalog.db"
src = sqlite3.connect(snap); out = sqlite3.connect(dst)
src.backup(out)                    # 用 Backup API，而不是复制 .db 文件
out.close(); src.close()
```

**应用必须已经退出**再做这一步。恢复完成后正常启动即可。

### 实测输出（在冻结现场的一份副本上跑的，副本已删）

```
覆盖前 catalog.db = 864256 字节｜文档数 = 273
Backup API 覆盖完成｜dst 大小 = 864256 字节｜journal_mode = wal
恢复后首启： 结构版本 schema_version = 3 / 文档主记录 = 0（其中标记缺失 0） / 分类 = 14，标签 = 0 /
            监测根目录 = 0 / 任务 = 无任务 / 应用内部状态条数 = 1 / 库文件 = ...\data_root\data\catalog.db
```

### 第 2 步：恢复之后必须知道的三件事

1. **结构会自动升回最新版**。`pre-migration-0002` 那份停在 v1，启动时迁移 0002/0003 重跑一遍，
   所以恢复后看到的还是 `schema_version = 3`，同时 `backups\` 里**多出新的快照**（实测多出
   `pre-migration-0003-20261015T035159.db`）。这是设计行为，不是异常。
2. **人工成果退回快照时刻**。上面的实测里 `文档主记录 = 0`：选中的那份快照是**建库之前**的状态，
   它里面根本没有 `text_pages` 表、`documents` 是 0 行。所以"恢复到哪一天"要看文件名里那个
   序号 + `@v` 版本，不要凭感觉选。**默认分类会被重新种一次**（实测 14 个）。
3. **监测根要重新登记**。快照里 `roots` 是空的 → 恢复后 `监测根目录 = 0` → 应用不会扫任何目录。
   在 S7「设置与状态」→「监测目录」点「添加目录…」重新登记（批量登记见 `docs/USAGE.md` §四 的命令行），
   然后一次全量扫描就能把 C 档数据重建回来：

```
重扫： ...corpus：PDF 273｜新增 273｜改动 0｜改名 0｜未见 0｜未变 0｜排队索引 273（329 ms）
队列排空 2.4s｜状态 = {'done': 273}
重扫后可检索「冷链物流」= 3 条｜正文花名册 = 正文 543 行｜索引花名册 543 行｜未进索引 0｜花名册残留 0
```

—— 原生正文 543 行全部回来了，检索照旧能用。**唯独那 1 页 OCR 文本没有**（543 ≠ 备份前的 544），
这一行差异就是 §一 说的"OCR 属 B 档"的实测证据。

## 五、恢复完怎么确认没恢复坏

跑一致性核查探针（**只读**，不写库、不动文件）：

```
.venv\Scripts\python.exe tests\probes\p12_consistency.py --data-root "D:\归档库"
```

实测输出（对冻结冒烟现场，273 份 / 544 页）：

```
数据根：C:\Users\...\frozen_smoke_1015_032932\data_root（来源：显式参数）｜库：catalog.db
  绿  C0  水位停在迁移目录里的最新版
        库里 v3｜迁移目录最新 v3｜迁移清单 ['0001_initial', '0002_text_and_fts', '0003_ocr_tracking']
  绿  C1  库自身健康（integrity_check 与外键）
```

两条使用注意：

- **未验 ≠ 通过**。加 `--no-file-walk` 会跳过盘上遍历，那几条显式印成「未验」并让整场变红。
- 应用正在跑时可能读到需要恢复的 WAL，探针会**原样把这句话打给你**并且不改库。这时先关应用再跑。

## 六、绝对不要做的事

| 不要 | 为什么 |
| --- | --- |
| 清空 / 删除 `<数据根>\data\` 目录"重来一遍" | 里面可能有无法再生的 OCR 文本（169 天口径，ISSUES I22）和全部人工分类标签。先按 §三 备份 |
| 应用运行时只拷 `catalog.db` | WAL 下会拷到不一致状态。用 §三 做法 A（先关）或做法 B（Backup API） |
| 把快照复制成 `catalog.db`（`shutil.copy`） | 同上。用 `src.backup(dst)` |
| 直接编辑 `settings.json` 里的手填路径来"改库" | 库是事实来源，路径口径由扫描器算。改错会造出一批 `missing` 记录 |
| 以为"恢复数据库 = 恢复 PDF 文件" | **完全两件事。** 数据库只记路径与元数据，本程序从备份角度是"文件清单"，不是"文件仓库"。PDF 丢了它变不出来（A 档）。`file_operations` + `operation_items` 记的是"文件被本程序移动过"的历史，S3「执行归档」与 S4「整批撤销」会真的改动磁盘（**ISSUES I55** 已销账，2026-10-17），所以**这份台账本身就是你不能丢的东西** —— 库没了就没人知道你把这些文件搬到哪去了 |

### §八·附 备份包压缩：实测数字（2026-10-31，真库 12,121,096,192 B）

| 做法（对象 = `catalog.db`） | 产物字节 | 比值 | 压缩耗时 | 折算 | 解压回程 |
| --- | --- | --- | --- | --- | --- |
| 直接拷（今天的备份包形状） | 12,121,096,192 | 1.0000 | **21.5 s** | ≈538.6 MiB/s | 不适用（回去也是拷） |
| zlib level 1 | 8,520,311,278 | **0.7029** | 361.5 s | ≈32.0 MiB/s | **未测**（第一场探针在选定 codec 后崩在传感器自己写的 `fout.tell()`，见 **I123** ③） |
| lzma preset 1 | 7,638,111,344 | **0.6302** | 2,382.3 s | ≈4.9 MiB/s | **469.7 s**（24.6 MiB/s），12,121,096,192 B 逐字节回还 |

| 做法（对象 = `vectors.npy`，1,073,741,952 B） | 产物字节 | 比值 | 压缩耗时 | 解压回程 |
| --- | --- | --- | --- | --- |
| lzma preset 1 | 590,001,812 | **0.5495** | 203.0 s | **32.9 s**（31.2 MiB/s） |
| 直接拷 | 1,073,741,952 | 1.0000 | **2.8 s**（370.8 MiB/s） | 不适用 |

**速度口径**：本表一律 **MiB/s**（字节 ÷ 2²⁰ ÷ 秒），三只探针用同一个除数，不与十进制 MB/s 混用。
⚠️ **直接拷那两行是 22:45 另一次实测**（`.probe_work/u49_rawcopy_baseline.log`，配对负载 **CPU 67.9%／可用
5,864 MiB**，压缩那三段是 21:16–22:05 跑的、没有配对负载读数）⇒ 上面两个倍率是**同日同机的量级对照**，
不是同一秒的分母。**更要紧的一条**：同一个库、同一台机，直接拷在轮三十（2026-10-27，
`docs/VERIFICATION-RUNLOGS-ARCHIVE-3.md` 记 12,112,449,536 B｜47.4s）量到 **47.4 秒**，今天量到 **21.5 秒**，
**同一个操作差 2.2 倍** —— 所以 ③ 的定案**不建立在这个倍率上**，而建立在 lzma 那 **39.7 分钟**本身：
分子是直接量到的，分母无论取 21.5 还是 47.4，结论同向。表上原先那行「47.4 s ≈255 MB/s（今天的形状）」
是把轮三十的读数当成今天的分母用（字节数也不同），2026-10-31 收尾时就地改成同日实测，
返工点记 `docs/VERIFICATION-RUNLOGS.md` §4.60。

回读对账口径：两份解压产物都比**字节数**，再各比**头 64 MiB 与尾 64 MiB** 的逐字节相等
（`size_matches / head64_ok / tail64_ok` 三旗全真）。为什么只比两头而不比整库 sha256：
比整库要把 12.1 GB 再读一遍、再加一遍计算，而这一段要回答的问题只是"压进去的东西出不出的来"，
首尾两条带 + 全长字节数已经把它证伪得开了 —— 中间若有错，字节数或两端必有一条先红。
实测脚本 `.probe_work/u49_backup_compress.py`（压缩三段 + 那次崩溃）与 `.probe_work/u49_decompress.py`
（解压两段），原始读数 `.probe_work/u49_backup_compress.log` / `.probe_work/u49_decompress.log`。

读下来的结论写在这里，不是建议：**压掉 30% 的体积要付 16.8 倍的时间**（库的 `freelist_count=1`，
几乎没有空闲页可捡，所以省下来的全是 SQLite 页里本来就重复的那点）。
⚠️ **追注（同日补齐 lzma 与解压两条腿后的定案读法）**：换 lzma 只比 zlib 多省 7 个百分点
（0.7029 → 0.6302），时间却从 16.8× 涨到 **110.8×**（361.5 s → 2,382.3 s）；`vectors.npy` 确实压得动
（0.5495，比探针自己"int8 大概率压不动"的预估好），但两个成员一起压，整包也就从 13.19 GB 落到
8.23 GB（**0.6236**）—— 省 38%，代价是**一次备份 43 分钟、一次恢复 8.4 分钟**，而今天直接拷这两个成员
是 **21.5 + 2.8 ≈ 24.3 秒**（背靠背各测一次，不是一次整包计时）。按这个库的量级（10,991 份 / 197.6 万页，重跑嵌入 **450.4 分钟** 已在 **I112** 记过），
把备份做成一小时级别不是"更稳"，是让人**更少去点它**。
⇒ **③ 定案 = 丙：产品不做压缩**，只把包的实际体积如实写在界面与文档里（**D-071**）。
