# 技术决策记录

一个决策一条。**只记会影响多个模块、回退成本高、或下一个人一定会想改回来的选择。**
每条必须有实测证据或明确标注 `[推算]` / `[约定]` —— 没有来源的数字不接受。

状态含义：`已采纳` = 现在就按这个做；`已采纳-待确认` = 我按它实现了但需要你对边界点头；
`候选` = 还没定，别当已定事实引用；`已否决` = 试过了，理由写清免得重踩。

## D-001 UI 框架用 PySide6，且钉死 6.8.3 · 已采纳

**背景**：SPEC 要原生 Windows 桌面程序，需要本地文件系统访问、多线程、原生菜单快捷键。
**决策**：`PySide6==6.8.3`（含 Essentials/Addons/shiboken6 同版本），上界不放开。
**替代方案**：Electron/Tauri（没有本地 SQLite+FTS5 与 ONNX 生态，还要跨语言 IPC）；Tkinter（撑不起虚拟化表格与 PDF 阅读）；
PyQt6（许可协议差异，且同样有版本兼容问题）。
**被否的方案**：`PySide6 6.12.0` —— 装得上，`import PySide6.QtCore` 报 `WinError 127`，
`ctypes.WinDLL('Qt6Core.dll')` 同样 127，即 Qt6.12 引用了本机 user32/kernel32 没有的导出。证据 p3。
**后果**：6.8 是 LTS 线，安全；但意味着不能用 6.9+ 的新 API，升级前必须重跑 p3+p8。

## D-002 推理后端只允许一个 ORT 发行版：`onnxruntime-directml==1.20.1` · 已采纳

**背景**：需要本地 OCR 与本地嵌入，硬件 GTX 1060 Pascal。
**决策**：依赖树里只允许 `onnxruntime-directml==1.20.1`（自带 CPU EP，够兜底）。
**替代方案**：`onnxruntime-gpu`（要 CUDA，见 D-003）；双发行版并存（见下）；纯 CPU（OCR 慢 6.36×，见 D-006）。
**为什么不是"装个 CPU 版再说"**：`onnxruntime` 与 `onnxruntime-directml` 往**同一个 `onnxruntime/` 目录**写文件，
共存的结果不是报错而是 `import onnxruntime` **直接段错误 exit 139**，异常都捕不到。
**版本上限来源**：逐版本二分实测 1.19.2 OK / 1.20.1 OK / 1.21.0 起全部 `WinError 1114`（DLL 初始化例程失败）。
排除过的伪线索：PE 导入表依赖齐全；`api-ms-win-core-path` 是 API set 虚拟项；`msvcp140` 是 14.51 新版。
**后果**：必须常驻一条依赖守卫（`tests/guards/test_dependency_pins.py`，门禁 G21），
且 `pip check` 那条 `rapidocr-onnxruntime requires onnxruntime, which is not installed` 是**预期噪声**，
写死在白名单里，不许有人"顺手修好"它。

## D-003 不使用 CUDA · 已采纳（证伪了原假设）

**背景**：SPEC 第五节点名"不要因为 GTX 1060 支持 CUDA 就假设所有模型和推理后端均兼容"。
**决策**：代码里不存在 CUDAExecutionProvider 这条路径；GPU 一律走 DirectML，CPU 兜底。
**证据**：`get_available_providers()` 实测返回 `['DmlExecutionProvider','CPUExecutionProvider']`；
叠加 Pascal(sm_61) 在现代 CUDA 12/13 已弃用。
**后果**：DirectML 在 Pascal 上确实快（OCR 6.36×、嵌入 7.8×），但显存余量小（D-008 的串行要求由此而来）。

## D-004 全文检索用 FTS5 `trigram` + 短查询 LIKE 回退 · 已采纳-待确认（= RISKS Q1）

**背景**：中文正文要能全文搜。SPEC 未指定分词方案。
**决策**：external-content FTS5 表用 `tokenize='trigram'`；查询 <3 字符时**显式**走 `LIKE` 回退分支。
**证据**（p1，30 万行真实中文）：`unicode61` 中文**命中 0**（不报错，静默空结果）；
`trigram` 4 字查询 6.39ms、索引膨胀 6.91×；`bigram`（自切 2 字）4 字 6.95ms 但 2 字只要 1.42ms，索引 14.83×。
**替代方案**：`bigram`（短查询快 350×，代价是索引翻倍）；jieba 分词（词典切词对专名/混排不稳，且加一个运行时依赖）。
**为什么还挂着待确认**：选型取决于用户更在意体积还是 2 字词命中速度，我不替你选。
**后果**：`trigram` 对 1–2 字查询无能为力，这条必须在 UI 上显示出来，否则用户以为"搜不到=没有"。

## D-005 文件身份 = `realpath` 归一 + `COLLATE NOCASE` 唯一索引 · 已采纳

**背景**：同一份 PDF 可能以大小写变体、8.3 短名、冗余分隔符、重叠监测根出现在库里。
**决策**：`identity_key = norm(path).casefold()`，`norm` 必走 `os.path.realpath` 再 `normpath`；
主表 `path_key TEXT NOT NULL COLLATE NOCASE` + 唯一索引。
**为什么不是 `normpath`**：8.3 短名把空格吃掉（`报告 A.pdf` → `报告A~1.PDF`），纯字符串规范化归一不了，
实测 `realpath` 之后短名与长名的 identity_key 才一致（p7）。
**替代方案**：只按内容 hash 认同一文件 —— 已被 p7 否掉：同内容不同路径必须保持**两条不同记录**
（用户可能就是要留两份），去重是"报告重复"而不是"合并记录"。
**后果**：`LongPathsEnabled=1` 是本机现状不是目标机前提，阶段 4 归档路径生成前必须自检（ISSUES I10）。

## D-006 OCR 不进自动索引流程，改为用户显式触发 · 已采纳（Q3 已于 2026-10-15 勾选「甲 · 只跑我显式选中的」；Q2 索引体积仍未答）

**背景**：SPEC 阶段 5 原写"对扫描件建立 OCR 索引"。
**决策**：扫描器只**标记**"疑似扫描件"，OCR 由用户按目录/按文件触发，可断点续跑。
**证据**（p5 孤跑，真实扫描页 14 页）：CPU 25,835ms/页、DirectML 4,062ms 均值（中位 3,281ms）；
按 p0/p2 真实量级外推待 OCR **1,014,112 页** → **1,144h(GPU) / 7,278h(CPU)**，即 8h/天 × **143 个工作日**。
阈值不是我拍的：由"8 小时无人值守窗口推进 ≥10% 待 OCR 页"反算 = **284ms/页**，实测差 11.6×。
**「整库要多久」只允许一个口径（阶段 5 收工时定的）**：产品口径是 **169 天**，按已落地的每日页预算
6,000 页/日 折算（D-028）；上面那个 143 天是 p5 孤跑时期"纯推理小时 ÷ 8h"的算法，**不含出图与落库开销**，
只作为历史推导保留，不许再被引用成"要跑多久"。两个数不是矛盾，是两个口径 —— 现在写死只准用前者。
**为什么保留 RED 不改成绿**：调低阈值就能让探针通过，但那是把产品承诺改成能过测的样子。SPEC 明令不许伪装成功。
（2026-10-15：这条 RED 已由 D-028 作废重定为两条可过的限量，不是被"调阈值"调绿的。）
**替代方案**：换更大模型（更慢）；换 PaddleOCR（依赖体积与打包风险更大，且无现成 DirectML 路线）。
**后果**：OCR 文本按 B 档（难再生）**纳入备份** —— 理论上可再生，实测代价 169 天（预算口径），事实上不可再生；
而备份/恢复本身是阶段 4，还没实现 → 见 **ISSUES I22**。

## D-007 嵌入默认 fp32 + DirectML，量化不作为提速手段 · 已采纳

**背景**：语义层需要本地向量，不能装 torch。
**决策**：ONNX BERT + `tokenizers`（无 torch），默认 `model_optimized.onnx`(fp32 90.4MB) + DirectML。
**证据**（p6，320 个真实文本块 × 20 批）：fp32+DML **146.9 chunks/s**（全量 404 万块 = 7.6h）；
fp32+CPU 18.8；**int8+DML 只有 79.3，比 fp32 慢 1.85×**。
**被否的假设**："量化一定更快" —— 在 DirectML/Pascal 上实测反向。int8 只用于省体积（向量库 7.71GB→1.93GB）。
**关键实现约束**：mean-pooling 必须用**真实 attention_mask**。
`tokenizers` 默认不 padding，需要 `enable_truncation + enable_padding`；`token_type_ids` 由 `np.zeros_like(ids)` 补
（单句输入下等价正确）。当时如果传全 0 mask，池化出来全是零向量，相似度指标依然"看起来正常"—— 这条已进反向测试表。
**后果**：语义层比 OCR 便宜两个数量级（7.6h vs 1144h），但它依赖"已有文本"，扫描页没文本就只有空向量。

## D-008 GPU 任务全局串行 · 已采纳

**背景**：OCR 与嵌入都想用 GPU。
**决策**：任务队列保证同一时刻最多一个 GPU 任务；OCR/嵌入可被阅读器让位。
**证据**（p5）：本机空闲显存 **1369MiB**，单进程 OCR 吃掉 **701MiB** 后剩 668MiB，放不下第二个。
**后果**：吞吐上限被显存锁死，加 worker 数不会让 GPU 侧变快。

## D-009 监测事件不作为唯一变更来源 · 已采纳

**背景**：SPEC 3.1 要目录监测。
**决策**：事件流只做"加速"，**周期性全量对账扫描**才是权威；另有监听根存在性自检。
**证据**（p4，10 条断言全绿）：300 文件批量 **0 丢失**；但**被监听目录本身被重命名 → 0 事件**
（observer 还挂在旧句柄上）；跨目录移动上报成 `created+deleted` 而非 `moved`；停止监听期间的变更事件流永远看不见。
**替代方案**：只信事件（已否，会长期不一致）；轮询全盘（p0 全量扫描数分钟量级，扛不住高频）。
**后果**：G12 门禁（根被改名 ≤60s 自愈）目前是 **[约定]** 阈值，还没实现。

## D-010 打包用 PyInstaller `--onedir` · 已采纳

**背景**：SPEC 要可分发的 Windows 程序。
**决策**：`--onedir`，产物 247.6MB，构建 267.3s。
**证据**（p8）：冻结 exe 冒烟实测 PyMuPDF 1.28.2 建 PDF、**FTS5 trigram 真实命中中文**、ORT 1.20.1 带 DML、Qt 6.8.3 建控件 ——
冻结环境最容易丢的正是 FTS5 扩展与 ORT 的 dll，这条是**跑过**不是"应该没问题"。
**替代方案**：Nuitka（编译期更长，未验证）；`--onefile`（**未测**，解压到临时目录会让"数据目录在哪"变复杂，ISSUES I14）；
MSIX（分发热更重，单机自用不值）。
**后果**：`--hidden-import` 写错不会报错，所以冒烟必须**真的执行**功能而非 import 成功即算过。

## D-011 全文索引只覆盖"子集"而非全库 · 候选（= RISKS Q2，未定）

**背景**：本轮新算出来的约束 —— p2 实测中位 2,294.6 字/页 × 100.8 万文本页 ≈ 正文 6.9GB，
乘实测膨胀率 4.03–6.91× → FTS 索引 **28–48GB**；×10 压力档 280–480GB，直接不可行。

**状态**：**候选**。这改的是产品定义（"能不能搜到全部正文"），必须你点头，我不自行实施。

## D-012 测试一律用真实 SQLite，禁止 mock 数据库 · 已采纳

**背景**：本项目最容易出的错都是"不报错但结果错"。
**决策**：L2/L3 一律真实 SQLite 文件/内存库。
**理由**（p1）：`unicode61` 中文静默零命中、`'delete'` 命令少带一列静默留幽灵行、FTS5 根本没有 `offsets()`
—— 这三件在 mock 里永远测不出来。
**后果**：测试比 mock 慢，但换来的是 G10 那三个方向（`unindexed` / `stale_docsize` / 带词 `MATCH`）真的能变红。
**2026-10-15 更正**：本条原先写的是"换来的是 G10（幽灵行数 = 0）这类断言真的能变红"，而当时那条
**免词**计数在外部内容表上恒等于正文行数， mock 换成真库也照样不会红 —— 换库不等于换对了口径，见 **ISSUES I8** 与 p14。

## D-015 FTS5 外部内容表的硬规则 · 已验证

**背景**：全文层是产品的第一优先级，而 SQLite FTS5 有三处"不报错但结果错"的坑。
**决策**：接法一律以 **`DATABASE.md` 三** 为准（那份是实现时可对照的清单，本条不重复列，免得两处规则各改各的）。
**证据**（p1）：
- 外部内容表 `'delete'` 命令**漏带被索引列**不报错，但留下一条**删不掉的幽灵行**，此后任何按 docid 的检索都脏；
- `unicode61` 分词器下中文命中数 **0**（静默，不抛异常）；
- `offsets()` 在 FTS5 **根本不存在** —— `pragma_function_list` 只列出 `rank/snippet/bm25/highlight`，
  所以命中偏移只能在 Python 侧算；
- 列名与 content 表不一致时 `'rebuild'` 直接 `SQL logic error`。
**替代方案**：`content=''`（contentless）表 —— 省体积但无法取回原文片段，与"命中必须显示原文"冲突（已否）；
自己写倒排 —— 等于重写 SQLite 最重的部分（已否，违反 AGENTS.md「成熟库优先」）。
**后果**：G10 门禁 = `check_fts_consistency()` 的 `unindexed` 与 `stale_docsize` 都为 0，且带词 `MATCH`
的命中数等于 `MATCH` 再 JOIN 正文表后的命中数；这条只能在真实 SQLite 上测，见 D-012。
**幽灵的可测性本身也被实测过**（2026-10-15，`tests/probes/p14_fts_instrument.py`）：上面第一条那种坏法
是**免词口径唯一看不见**的一种，`'integrity-check'` 四种坏状态全部"通过"，所以判据里必须留一条带词的 `MATCH`。

## D-016 全文库与向量库分库存放 · 部分采纳（全文侧已落地，见 D-024）

**背景**：两套索引的体积与重建代价差一个量级。
**依据**：p1 实测 trigram 索引 ≈ 原文 **6.9×**；p6 实测 4,044,409 chunk × 512 维 fp32 ≈ **7.71GB**。
**决策**：`catalog.db`（记录 + 正文 + FTS，实际文件名见 `config/paths.catalog_db`）与
`semantic.db`（向量）**分文件**，各自可独立删除重建，
分库让 D-011 的"子集索引"和未来"向量库换 ANN 索引"两条改动互不牵连。
**状态**：全文那一半**已落地**（阶段 2 的迁移 0002，同库理由与代价见 **D-024**）；
向量那一半仍**未定** —— 具体分界待 Q2（索引体积策略）与 Q6（向量选型）拍板后写进 `DATABASE.md` 一。
**替代方案**：单库存一张向量表（SQLite 没有向量类型，只能 BLOB + 全表扫，400 万条下不可接受）。

## D-017 阅读器渲染以 PyMuPDF 为主，QtPdf 备选 · 已验证

**背景**：SPEC 要内置阅读器，两条通道都在阶段 0 实测过。
**依据**（p3）：fitz 渲染中位 **135ms/页**、QtPdf **43–50ms/页**（首次 26.1ms）；两条通道都能出图。
**决策**：默认走 PyMuPDF —— 它同时是文本提取、OCR 预处理、加密检测、`is_repaired` 判定的唯一入口，
阅读器复用同一个已打开文档对象，避免同一份 PDF 被两个库各开一次句柄。
**代价（如实记）**：QtPdf 渲染**更快**，选 fitz 是选"单句柄 + 功能重合"，不是选性能；
若后续**翻页延迟**过不了，QtPdf 是现成的替换点（渲染层已经隔离在 `parsing/` 之外）。
> **追加更正（2026-10-15，出 S2 线框时抓到）**：本句原文写的是"若后续 **G7**（翻页延迟）过不了"，
> 而 G7 在 `docs/TESTING.md` 第二节是「单 worker 处理完一个文件后的 **RSS 回落 ≤100MB**」，与阅读器毫无关系。
> 真实情况更难看：**阅读器的翻页延迟从来没有过任何门禁**，所以"过不了"当时是无从判定的。
> 判据要新立（现写作「新 · 翻页到出图 ≤ 400ms **[约定]**」，见 `docs/UI-WIREFRAMES.md` §S2），
> 编号问题记 **ISSUES I39**。与 ISSUES I28（门禁标签撞 G 编号）、ISSUES I34（归并表指向不存在的编号）同一类：文档里的证据指针没被机器核对过。
**替代方案**：pdf.js（要引入浏览器控件或本地服务，体积与离线边界都不划算，已否）；
外部 Acrobat/浏览器打开（违反 SPEC「内置阅读器」）。

## D-018 阶段 1 的 UI 只做「注册表驱动的运行时外壳」，不做任何一屏布局 · 已采纳（追溯请你确认）

**背景**：两条硬要求正面冲突 —— 你的阶段 1 指令要求"必须是真实运行的 UI，而不是静态截图或不可交互的设计稿"，
AGENTS.md 又禁止"线框未经逐屏确认前写界面代码"，而 Q7（屏数 A/B/A′）还没答。
**决策**：只写不会替 Q7 做决定的部分 —— 窗口 + 左侧导航列表 + 右侧堆叠页 + 状态栏；

## D-020 默认分类模板用「已种过」标记判定，不靠判空表 · 已采纳

## D-022 日志时间戳唯一口径：UTC ISO 8601 带 `Z`，三个出口一致 · 已采纳

**背景**：库里时间已经是 `now_ts()`（UTC unix 秒）一处口径；但日志最初是
`datetime.now(timezone.utc).astimezone()` —— 输出 `+08:00` 偏移，而 `app.log` 的行首还用的是
标准库默认 `asctime`（**本地时间、不带任何偏移标记**）。远程对账时对方要靠猜本机时区才能把

**决策**：`diagnostics/logs.log_stamp()` 是唯一写法（UTC + `Z`），`app.log` 通过自定义
`_StampFormatter.formatTime` 走同一条路，`crash.log` 段头与 `state.log` 的 `ts` 都用它；
正则 `STAMP_RE` 就定义在旁边，测试按它断言（口径定义在代码里，不散落在测试里）。
**证据**：`test_三个日志出口用同一个时间口径` 断言两件事 —— 三处格式都匹配 `STAMP_RE`，
且同一次启动的 `app.log` 首行与 `state.log` 的 `startup.begin` 指同一瞬间（差 <5s）。
注入 ISSUES I16（裸本地时间却标 `Z`：**格式完全合法、时刻差 8 小时**）只有第二条断言能抓到，

## D-023 结构迁移用「文件式脚本 + 单行版本水位 + 先快照后动结构」，不引入 alembic · 已采纳

**背景**：阶段 2 起库里就会有真实扫描结果，改表不能再靠删库重建；你的指令里"数据库能够初始化、写入、读取和迁移"
与 SPEC 3.8"操作可回退"在这里正面相遇。
**决策**（四条，逐条可断言，实现细节见 `DATABASE.md` 四）：
1. 一个迁移 = 一个文件 `db/migrations/NNNN_slug.py`，导出 `VERSION` 与 `apply(conn)`，靠
   `importlib.util.spec_from_file_location` 加载，不建包内注册表；
2. 版本水位是 `schema_version` 表的**单行**（`version` + `applied_at`），不写日志表、不数文件个数；
3. 动结构前必须有快照：`backup_dir` 为空 → **直接拒绝迁移**，不做"没备份也照跑"的降级；
4. 连接设 `isolation_level = None`，迁移自己发 `BEGIN IMMEDIATE` / `COMMIT` / `ROLLBACK`，
   失败时异常对象带 `db=` 与 `.snapshot`。
**为什么是第 4 条这种做法**：SQLite 的隐式事务会在 DDL 前后偷偷提交，"中途失败回到原样"就没法保证；
`BEGIN IMMEDIATE` 同时把并发写者挡在门外（WAL 下别的连接拿不到写锁）。
**替代方案（都否掉了）**：
- **alembic**：多一个依赖，而且它的工作假设允许"重建库"，与"绝不丢用户已确认的分类/标签"冲突；
  PyInstaller 冻结下还要处理它的模板与 `script_location` 路径（阶段 0 的 p8 已证明冻结环境里资源路径是坑）。
- **迁移 SQL 内嵌成字符串数组**：改动在 diff 里读不出意图，版本和水位也容易被顺手改成两处。
- **失败后拿备份文件恢复**：恢复窗口比回滚长得多，而且会把迁移期间新写入的东西一起覆盖掉。
**证据**：`tests/guards/test_migrations.py`（带 3 标签 / 5 文档 / 1 分类的旧库升级后逐表行数不变、
`foreign_key_check` 空）、`test_迁移中途失败回到原样`、`test_迁移失败时异常里带快照路径`；
反向注入 ISSUES I6（去掉"无备份就拒绝"）和 ISSUES I7（把 `rollback` 换成 `COMMIT`）都被抓到。
**后果**：`0002` 将是本机制第一次带数据升级（`ROADMAP` 阶段 2），所以阶段 2 的第一件事是给它配
"升级前后逐表行数与内容比对"的守卫，而不是先写功能。


## D-024 正文与全文索引放进 `catalog.db` 本体，不另开分库 · 已采纳（细化 D-016）

**背景**：D-016 只说了"全文库与向量库分库存放"，没说全文索引本身在哪。阶段 2 要落 `text_pages` + `content_fts`，
两条路都能走：跟主记录同库，或另开一个 `content.db`。
**决策**：**同库**。FTS5 的外部内容表（`content='text_pages'`）只能指向**同一连接、同一文件**里有 rowid 的表
（p1 实测），分库就等于放弃外部内容表、把正文在 FTS 里再存一份 —— 按 p2 的膨胀率（4.03–6.91×），
202 万页要多拷几十 GB，正是 ISSUES I2 里那个数字。
**向量另库**仍然成立（D-016 的另一半没变）：404 万块 fp32 = 7.71GB，且它的重建成本与生命周期和正文完全不同。
**代价与对策**：正文和 FTS 写进主库之后，"索引塌了"会连主记录一起 risk，所以三条一起成立才有边界：
① 迁移前必须有快照（D-023 第 3 条，`backup_dir` 为空直接拒绝）；
② G10（FTS 与正文对齐）常驻每阶段门禁 —— **判据 2026-10-15 换过一次**：当时写的"幽灵行 = 0"是条
   免词计数，在外部内容表上恒等于正文行数、永远不会红，现在换成 `unindexed` / `stale_docsize` /
   带词 `MATCH` 三个方向（ISSUES I8、`tests/probes/p14_fts_instrument.py`）；
③ 正文只由 `index_service` 一处写（`texts.replace_pages`），别的路径改不到它。
**证据**：`tests/guards/test_migrations.py` 的"带数据升级后逐表行数不变 + `foreign_key_check` 空 + 幽灵行 0"。

## D-025 任务终态由队列一处判定；进度补齐写在仓储里，不指望处理函数记得 flush · 已采纳

**背景**：`index` 处理函数按 `PROGRESS_STEP_PAGES=64` 攒着写进度，最后一页不满步长就不写；
同时"处理函数正常返回"并不等于"它真的做完了"。
**决策**（三处各管一件事，都不许越界）：
1. **处理函数只有两支笔**：`ProgressMonitor` 能写进度、能问该不该停，拿不到 `JobRepository`
   —— 它一旦能直接写状态，就能写出状态表里不存在的流转；
2. **`done` 的补齐在 `JobRepository.succeed()` 里做**（`done = total`），不靠"处理函数记得先 `flush()`"
   这种没人保证的约定。「任务已完成」的定义就是工作量全部处理完，否则状态 `done` 而进度 92%，
   而 `sum_progress()` 把 done 行加起来的"已处理页数"会长期少算一截；
3. **收尾按库里的当前状态判流转**，不按内存里记着的那个：处理期间用户可能已经取消，
   这时 `running → done` 不合法，必须停手（`_finish_success` 重读一次行）。
**顺带定死的两个口径**：处理函数没抛 `JobCancelled` 就返回、但退出闸门已拉下 ⇒ 判 `cancelled` 不判 `done`
（判 `done` 等于把这文件永远标成"已处理"，而它只跑了一半；索引可重入，宁可重跑）；
被退出打断而留在 `running` 的那一行是 `recover()` 的输入，**不是 bug**，所以不用假终态去盖它。
**证据**：`test_进度按步长攒着写最后补齐`（反向注入 ISSUES I19 抓到）、`test_试满上限后不再算重试而是留下失败终态`（ISSUES I23）、
`test_进程被杀留下的running残尸重启后接着跑完`（e2e 真把行留在 running 再重开）。

## D-026 永久故障只消耗一次尝试，重试预算是留给瞬时故障的 · 已采纳

**背景**：截断的 PDF、需要口令的 PDF、整本读不出字的 PDF —— 重试第 2、第 3 次结果完全一样，
但每次启动都要重跑一遍，而状态页上它们永远"还在重试"，真正该看的故障反倒被埋掉。
**决策**：处理函数抛 `PermanentFailure` ⇒ 直接 `finish_as(..., "failed")` 并留原文，**不进 `retry_later`**；
其余异常 ⇒ `retry_later` 到 `DEFAULT_MAX_ATTEMPTS = 3` 为止。
`jobs` 表里没有第四种状态，"到第几次就放弃"的唯一持有者是 `WorkQueue.max_attempts`，界面读它而不是自己写一个 3
（`test_重试上限显示的是队列真正在用的那个数`）。
**代价**：分类必须判得准，判错了就把好文件永久打死。所以只有三种情形允许抛 `PermanentFailure`：
打开失败（`PdfOpenError`）、需要口令、**一页都没读出来**；坏页不算（其余页照写，`parse_status='degraded'`）。
**证据**：e2e `test_永久故障一次就定终态不把好文件拖在重试里` —— 截断与加密各 `("index","failed",1)`，同目录好文件全 `done`。

## D-027 接第三方库的回调，测试必须 import 产品里那个类；静默失灵要有唯一读数出口 · 已采纳

**背景**：阶段 2 抓出两个 bug，共同点是**失败了但没人看见** —— watchdog 处理器缺 `dispatch`
（observer 线程在第一条事件上死掉，`watched_roots` 照旧是 1）；
`threading.excepthook` 读不存在的 `args.exc_info`（钩子自己抛异常，worker 崩溃现场一行不剩）。
而阶段 1 的 p4 探针**自带一个处理器类**，所以它全绿的同时生产代码一次都没被调用过。
**决策**（两条都是流程性的，不是这次修完就算）：
1. **接线测试不许另写等价物**：测试要 `from pdfarchiver.fs.watcher import _BufferHandler, WatchManager`，
   用产品里的那个类去满足 watchdog 的回调契约（`test_处理器满足watchdog要求的回调形状`）。
2. **每一个"可能静默死掉"的东西都要有一个只读数字**，并且那个数字要能在读数为真时证明它不是恒真：
   `WatchManager.is_alive()` → `BackgroundState.watcher_alive`（**每次现读**，不缓存启动那一刻）→ 状态页 `⚠ 文件监听线程已不在`。
   配套断言是"半路真让它死一次"（`ctx.watch.stop()` 后再读一次快照），不是"构造一个死的状态"。
**为什么不选"加异常告警弹窗"**：Q7 未答，界面没确认过，不能为可观测性擅自加一屏（AGENTS.md 禁令）。
读数落在已批准的状态页里，是这一阶段唯一被允许的界面改动。
**证据**：反向注入 ISSUES I38–ISSUES I44 七条，其中 **ISSUES I43 第一版抓不到**（把 `watcher_alive=True` 注在"后台正在跑"的断言上，
那时监听确实是活的）—— 补了半路死亡的测试之后才有约束力。规则已同步进 `docs/ISSUES.md` 附「接第三方库的回调」一行。

## D-028 G13 作废重定：资源限量改成「每日页预算 + 单页超时」，两个数一律实测反算 · 已采纳（你勾选 甲）

**背景**：SPEC A-OCR-1 反算出 284ms/页 的单页预算，p5 实测最慢 3,281ms/页（DML），G13 从建立起就一直判 RED。
根因不是实现慢，是**假设本身错了**：GTX 1060 + DirectML 上，一本 946 页的书要 1,144 GPU 小时。
**决策**（四件，都不许退回"拍一个数"）：
1. **单页超时** `PAGE_TIMEOUT_MS = {"DmlExecutionProvider": 30_000, "CPUExecutionProvider": 165_000}`
   = p5 实测该档**最慢单页**（14,072 / 80,291ms）**×2** 后向上取整到 5s 格；没实测过的 provider 一律取最宽的一档
   （宁慢不误杀）。超时那页**不入库** —— 识别不可信时写进索引就是污染正文，整份停下等下次点名。
2. **每日页预算** `DEFAULT_DAILY_PAGE_BUDGET = 6000` = 8 小时无人值守 28,800s ÷ 实测**最慢可持续** 4.193s/页
   （p5 DML 均值 4,061.8ms + P11 在产品路径上实测的出图与落库开销 131.4ms）≈ 6,868 页 → 向下取整到千位。
   预算用**均值**而不是最大值：最大值已由单页超时管，预算管的是"一天吞得下多少"。
3. **限量是止血，不是让整库跑得完**：全库待 OCR 1,014,112 页 ÷ 6,000/日 ≈ **169 天**。这句话必须写在文档里，
   否则下一个人会把"每日 6,000"读成"分三天跑完"。
4. 用满即停走 `JobCancelled`（第三种停，见 D-030）：任务落 `cancelled` 终态、文档 `partial`/`pending`、
   未跑的页留在待办；**不消耗重试预算**（`attempts` 不加），否则同一份文档会把预算反复吃掉。
**为什么不选"降低 OCR 质量换速度"**：那改的是识别结果的可信度，而阶段 5 的红线是"不得把未经验证的识别文字
伪装成准确的原始文本"（SPEC 五）。
**证据**：`tests/unit/test_ocr_limits.py` 六条钉的是**推导关系**而不是数字本身（改数必须同时改实测出处：
`test_单页上限是实测最大值乘二`、`test_每日预算是最慢档八小时跑不满的那个数`）；
反向注入 ISSUES I32–ISSUES I45 十四条（含 ISSUES I42「上限松到 ×4 以上」、ISSUES I44「预算拍成一个够不着的大数」）。

## D-029 OCR 幂等判据落在「页」，版本指纹故意不含 provider · 已采纳

**背景**：整库重跑 = 1,144 GPU 小时级别的事故；永不重跑 = 换了引擎还宣称"这本书搜得全"。两个方向都不可接受。
**决策**：幂等的最小单位是**页**，指纹存在 `text_pages.ocr_version`（`0003` 加列，你勾选 甲）：
`rapidocr-onnxruntime/1.4.4+onnxruntime/1.20.1+dpi200`。`ocr_is_current()` 要**页数、版本、逐页指纹**三项同时成立。
- **不写 `DmlExecutionProvider`**：换显卡或驱动不改识别结果，写进去等于每次驱动升级让整库过期（ISSUES I21 抓到过这条）；
- **写 DPI**：换档真的改结果，所以 `OCR_DPI` 由 `test_出图分辨率钉在实测那一档` 钉死，改 DPI 必须重做实测（ISSUES I30）；
- 版本读不到就报错点名是哪个包、怎么装，**不许编一个 `unknown` 充数**（ISSUES I22）。

## D-030 队列有三种「停」，收尾各不相同 · 已采纳

**背景**：阶段 5 第一条集成测试就失败在这一点上 —— 预算停在半路的 OCR 任务等不到空闲。
原实现把"退出打断"和"处理函数判停"混成一支笔（只看 `_stop.is_set()`），于是处理函数自己判停的任务
被留在 `running`，而它明明已经停了。
**决策**：`_finish_cancelled()` 按优先级分三支，顺序不可颠倒：
1. 库里已是 `cancelled`（用户请求取消先行落状态）⇒ 不再动；
2. `_stop.is_set()`（退出闸门拉下）⇒ 留 `running` 给下次启动的 `recover()` —— 那次的"做完了"不可信；
3. 否则是**处理函数自己判停** ⇒ `finish_as("cancelled", error=原因)`，`JobCancelled` 的 message
   原样落进任务行的 `last_error`，因为界面要能回答「为什么停在这」。
**代价**：判停是终态、不自动重排 —— 这与 D-006「只跑显式点名的」一致：程序不许自己决定什么时候再来一遍。
**证据**：`test_处理函数自己判停时落cancelled并留下原因` 与 `test_退出闸门已拉下时处理函数判停仍按打断处理`
（两条各自独立地钉住第 3 支和第 2 支）、OCR 侧 `test_预算停在半路的任务不许记成跑完`；反向注入 ISSUES I37、ISSUES I38。

## D-031 OCR 文本永远标出处，失败页一行都不写 · 已采纳

## D-036 向量方案定丙（降密度）先行，且只给「已索引正文的页」建向量 · 已采纳

**背景**：ROADMAP **Q6** / docs/RISKS 2.5 的三个候选（甲 暴力 numpy 单库、乙 ANN+int8、丙 降 chunk 密度），

## D-048 · 跳过的项不进 journal（2026-10-15，ISSUES I42）

**决定**：被跳过的项（如冲突项默认跳过）**不进 journal**，journal 只记录真正执行过磁盘操作的项。

**理由**：
1. journal 的职责是崩溃恢复依据，只记真动过的就够了
2. `operation_items.state` 有 `skipped` 终态，台账层面已经记录"这项被跳过了"
3. 如果跳过的项也进 journal，恢复矩阵会看到"计划里有、日志里没有"的项，需要现编一个态，违反 AGENTS.md「同一个概念两处存放」

**后果**：
- `operation_items.state` 词表保持 `pending|done|failed|skipped`
- journal 态机保持七态（pending→copying→src_verified→dst_written→dst_verified→src_removed→done），不含 skipped
- 两边词表都加 CHECK 约束（迁移 0005）
- 断言：跳过的项在 `operation_items` 里是 `skipped`，但 journal 里没有对应行

## D-049 · 操作批次 ↔ 队列任务反查：`file_operations.job_id`（2026-10-15，ISSUES I43）

**决定**：给 `file_operations` 加 `job_id` 列（可空外键指向 `processing_jobs.id`），一个批次一条总控任务，`doc_id` 留 NULL。

**理由**：

## D-050 · 收尾写失败不许把任务留在 `running`：默认单 worker + 有界重试与同进程重放（2026-10-16，ISSUES I46 甲+乙）

**背景**：真实首扫最后 13 份卡在 `running`，`py-spy` 显示两个 worker 都在 `claim()` 的空队列分支上睡觉，
即那 13 行**没有主人**；错误原文是 `sqlite3.OperationalError: database is locked`，发生在**收尾那一行 UPDATE**。
两份 app.log 里 `收尾流程出错` 合计 27 次。排空判定 `queued + running` 因此永不归零，G2 被挡住。

**决定**：两件一起做，不选丙（`claim()` 领取心跳超时的 `running`）。
1. **甲** `worker_threads` 默认 **1**（`config/settings.py`），仍允许用户在 `settings.json` 覆盖回 2 —— 收的是默认值，不是禁能力。
2. **乙** 收尾写改成**有界重试**（`FINISH_WRITE_ATTEMPTS=3`，退避 `(1.0, 3.0)`，均为 `[约定]`）；
   预算烧光后把终态挂进 `_pending_finals`，由**同一 worker** 在每轮迭代开头与线程退出 `finally` 各重放一次；
   `IllegalTransition` **不重试也不重放**；`monitor.flush()` 包 try —— 进度写失败不得挡住落终态。

**理由**：
1. SQLite 只有单一写者，写密集的 `index` 任务开两个 worker 没有并行收益，只有互相抢写锁（27 次锁错误全部由它引起）
2. 丙治的是"进程被杀"，而现场是"进程活得好好的、行却没人管"（`recover()` 只在启动时跑一次），乙才对上病根
3. "退出打断故意留 `running`"（`recover()` 的输入）与"写失败留在 `running`"是两件事，后者必须在本进程内落终态

**后果**：
- 单条任务最坏收尾时长 `3×5s` 忙等 `+ 1+3s` 退避 ≈ **19s**，由 `test_收尾重试预算与退避表和忙等时长自洽` 断言 ≤30s `[约定]`
- 退避表长度必须 ≥ 预算-1，短一格会在 `except` 里 `IndexError`，**反而**把行留在 `running`（注入第 8 条实测点名）
- 7 条守卫在 `tests/integration/test_job_queue.py`，反向注入 11 条坏法全数「变红且点名」（2026-10-17 现测）
- 排空判定 `live_count()` / `wait_until_idle()` 的语义不变，但不再被无主 `running` 毒到
- **不销账**：验收口径要求「真语料最后 13 份排空 + `收尾流程出错` 前后对比读数」，那一条量完才改 CLOSED

## D-051 · 1–2 字正文检索改成"有界浅扫"，并且必须自报没扫完（2026-10-17，ISSUES I59 乙）

**背景**：G2 在真库（`text_pages` 1,972,578 行）实测 **P95 2,809ms** vs 红线 500ms，判 RED。
本轮把病因从"表太大"改成"第 200 条命中落在多深"——同一张表同一条 SQL，`发票` 走 334,924 行 2,676ms、

**ISSUES I60** 落地，但它**不让 P95 变快**；丙（2-gram 索引）按 docs/RISKS 2.9 要先反算 28–48GB 才许谈；

**决定**：给正文 LIKE 通道加**深度预算** `LIKE_SCAN_ROWS = 60_000` 行，到点就停，并且
**"没扫完"是结果的一部分**，不是日志里的一句话。
1. 仓储层 `TextRepository.search_like(…, scan_budget=N)` 多返回一个 `beyond`（窗口之外还有行）；
   `scan_budget=None` 时行为与旧版逐字一致，`beyond` 恒 False。
2. 实现取**边界探查 + `tp.doc_id <= 边界`**，不取"窗口子查询 JOIN 回主表"。
3. 服务层把它收成 `SearchResult.body_scan_incomplete`，`lines()` / `status_line()` 追加自报文案，

**理由**：
1. 窗口子查询那写法实测会把浅查询**拖慢**：`北京` 118ms → 358ms（探针 `.probe_work/i59_budget_shape_probe.py`

## D-056 · 队列 handler 的形状核对长在**构造点**，判据用 `bind()` 而不是数参数（2026-10-18，**ISSUES I68** 甲）
