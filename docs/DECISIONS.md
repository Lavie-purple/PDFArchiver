## D-040 S1 布局定案：三栏常驻；1024 档牺牲命中面板（变浮层）而不是分类树 · 已采纳

**背景**：D-039 只定了"一共几屏"，布局仍归 AGENTS.md 的线框闸门。S1 的两个高差异黑白线框
（甲 三栏常驻｜乙 一栏到底）出在 `docs/UI-WIREFRAMES.md` §S1，你 2026-10-15 回「跟你推荐选择」→
那三问全按推荐定。**这一条只定布局，没有解锁任何代码**：S2–S8 仍待逐屏确认。

**决策 · 三项**：
| 事项 | 定案 | 落成可断言的形状 |
| --- | --- | --- |
| 布局 | **甲 · 三栏常驻**（左：导航 + 分类树｜中：虚拟化文档列表｜右：命中面板） | 列表**行高统一** ⇒ `QTableView` 行号↔坐标换算保持 O(1)；出现"变行高展开"即判红 |
| **1024×720 这一档保留** | 放不下时**命中面板变浮层**（~420px，可关）+ **左树收成 48px 的条**（2026-10-17 按 **ISSUES I53** ①甲 定案改正措辞：条上是「分类」两字按钮、点开是真树浮层，不是每类一枚图标 —— `Category` 没有图标字段），文档列表吃掉剩余宽度 | 算术进测试：`236 + 480 + 360 = 1076 > 1024` ⇒ 必须且只牺牲一栏，**牺牲的是命中面板**（搜索是"要结果时才看结果"，树是"随时知道我在库的哪个位置"） |
| 已交付的「运行状态与自检」页 | **并入 S7 上半区，内容一字不改搬过去** | 屏数仍是 8，不重出清单（否则违反 D-039 与 AGENTS.md 的回环节 2）；`ui/nav.py` 的 `PAGE_STATUS` 从独立导航项变成 S7 的一部分 |

**为什么是甲（决定性理由不是偏好）**：乙 的"命中展开在文档行下面"会让行高随展开变化，
按需取行的虚拟化就得整表测高 —— 在 ×10 档 **8 万行**下就是 O(n²)，
是 AGENTS.md「禁止全量渲染 / 禁止 O(n²)」在本项目里**唯一会被 UI 自己犯掉**的位置
（阶段 0–5 的这条禁令一直只压在后端和文档上，没碰过列表控件）。

**顺带定掉的一处含糊（线框自己前后不一致，我按项目既有规矩选诚实的那边）**：
S1 线框的左导航标称「9 项」而只画了 8 行，S8「分类与标签管理」当时是画成树面板底部一个按钮的。
**定案：S8 占一条独立导航项**（进"库与检索"分组，与 文档库 / 检索 并列），
并删掉线框里那个指向同一屏的重复入口按钮（AGENTS.md：每加一个新入口先全站搜是否已有同功能入口）——
把一整屏的入口藏进另一屏的按钮，等于让"应用能启动但看不见还剩什么没做"重新要靠脑补，
而那正是 `ui/nav.py` 那份注册表存在理由（D-018）。定案后左导航 = **9 项**，仍远低于分组阈值 20。

**代价（如实记）**：
- 1024 档下"边看命中边归类"这个主动作**退化成两步**（得先唤出浮层）；浮层的开/关状态要求可断言（不记忆成"每次都开"）。
- 已交付的 `ui/nav.py` 的条目形状要跟着变（8 项含 status → 9 项不含 status 而含 S8）；
  这一改动**留到线框全部确认完**再动，届时它是一次改导航注册表 + 改对应断言，不是偷偷加界面。
- 三条后果（行高统一 / 1024 浮层降级 / 状态页归属）都还没有断言在场 —— 断言只能在界面代码被允许写的那天一起写。

**落地回执（2026-10-17）**：上面那条"还没有断言在场"已经不成立，三条都有守卫了。
机械收在**一个**共用模块 `ui/tier.py`（`FloatablePanel` + `sync_tier`，S1 的左树与右详情、
S8 的左树一处规则三处用，AGENTS.md「同类问题不逐个打补丁」），断言在
`tests/integration/test_ui_tier.py`（本条落地时 9 条，**现数 20 条**、增段见 **D-052**，含本条要求的算术 `236 + 480 + 360 = 1076 > 1024`、
行高统一、浮层默认关可关、S8 在 1024 档收起），状态页归属由 `ui/pages/settings_page.py`
**嵌控件**而非抄渲染代码，守卫在 `tests/integration/test_status_readout.py`。
10 次坏法注入逐条真跑红并精确点名。**本条授权的形状没变，但有三处实现比线框少了一截**
（图标条上没有图标 / 右栏装的是详情不是命中列表 / 快捷键键位线框没给），逐条记在 **ISSUES I53**。
**2026-10-17 更正本段最后一句**：三处已按 **I53** 甲·甲·甲 定案收口（线框措辞照实改成"48px 的条 + 按钮 + 真树浮层"、

## D-050 · 收尾写失败不许把任务留在 `running`：默认单 worker + 有界重试与同进程重放（2026-10-16，ISSUES I46 甲+乙）

**背景**：真实首扫最后 13 份卡在 `running`，`py-spy` 显示两个 worker 都在 `claim()` 的空队列分支上睡觉，
即那 13 行**没有主人**；错误原文是 `sqlite3.OperationalError: database is locked`，发生在**收尾那一行 UPDATE**。
两份 app.log 里 `收尾流程出错` 合计 27 次。排空判定 `queued + running` 因此永不归零，G2 被挡住。

**决定**：两件一起做，不选丙（`claim()` 领取心跳超时的 `running`）。
1. **甲** `worker_threads` 默认 **1**（`config/settings.py`），仍允许用户在 `settings.json` 覆盖回 2 —— 收的是默认值，不是禁能力。
2. **乙** 收尾写改成**有界重试**（`FINISH_WRITE_ATTEMPTS=3`，退避 `(1.0, 3.0)`，均为 `[约定]`）；
   预算烧光后把终态挂进 `_pending_finals`，由**同一 worker** 在每轮迭代开头与线程退出 `finally` 各重放一次；
   `IllegalTransition` **不重试也不重放**；`monitor.flush()` 包 try —— 进度写失败不得挡住落终态。

**理由**：
1. SQLite 只有单一写者，写密集的 `index` 任务开两个 worker 没有并行收益，只有互相抢写锁（27 次锁错误全部由它引起）
2. 丙治的是"进程被杀"，而现场是"进程活得好好的、行却没人管"（`recover()` 只在启动时跑一次），乙才对上病根
3. "退出打断故意留 `running`"（`recover()` 的输入）与"写失败留在 `running`"是两件事，后者必须在本进程内落终态

**后果**：
- 单条任务最坏收尾时长 `3×5s` 忙等 `+ 1+3s` 退避 ≈ **19s**，由 `test_收尾重试预算与退避表和忙等时长自洽` 断言 ≤30s `[约定]`
- 退避表长度必须 ≥ 预算-1，短一格会在 `except` 里 `IndexError`，**反而**把行留在 `running`（注入第 8 条实测点名）
- 7 条守卫在 `tests/integration/test_job_queue.py`，反向注入 11 条坏法全数「变红且点名」（2026-10-17 现测）
- 排空判定 `live_count()` / `wait_until_idle()` 的语义不变，但不再被无主 `running` 毒到
- **不销账**：验收口径要求「真语料最后 13 份排空 + `收尾流程出错` 前后对比读数」，那一条量完才改 CLOSED

## D-060 · 迁移 0008 加浏览排序索引（2026-10-18，**ISSUES I77** 甲）

**背景**：`browse_documents` 默认按 `name COLLATE NOCASE` 排序，但这条表达式没有匹配的索引。
8 万份库的 `EXPLAIN QUERY PLAN` 显示 `SCAN d` + `USE TEMP B-TREE FOR ORDER BY`，库尾延迟 737 ms；
加一条 `CREATE INDEX ix_documents_name_ci ON documents(name COLLATE NOCASE)` 后降到 13 ms（**58×**），
写入侧每份文档 +7.4%（3,000 份探针：1.208 s → 1.297 s），索引构建 0.364 s@8 万份。

**决定**（四条，每条都可断言）：

1. **纯加索引，不动表/列/数据**：`0008_name_ci_index.py` 只含一条 `CREATE INDEX IF NOT EXISTS`，
   回滚是 `DROP INDEX IF EXISTS`。`IF NOT EXISTS` 是因为探针在临时库里手动建过同名索引再跑迁移，
   不能撞 `already exists`。
2. **不跑 `ANALYZE`**：实测加索引前后 `EXPLAIN QUERY PLAN` 都是 `SCAN d USING INDEX ix_documents_name_ci`，
   加不加 `ANALYZE` 计划不变、延迟差异在噪声内（12.7 → 13.8 ms@79,950）；而 `ANALYZE` 是 O(库大小)
   的慢操作，按 AGENTS.md「慢操作只许放在显式慢路径」不许塞进迁移。
3. **守卫用 `SORTS["name"]` 直接取产品模块**：`tests/guards/test_migrations.py` 新增
   `test_空库经迁移链建出的库把name排序交给索引`，断言 `EXPLAIN QUERY PLAN` 不含
   `USE TEMP B-TREE FOR ORDER BY` 且含 `ix_documents_name_ci`。因为 SQL 是从 `SORTS["name"]` 拼的，
   改排序口径时守卫自动跟着变（不会守着一条与产品脱钩的索引）。
4. **坏法真注入过**：`.probe_work/i77_badway.py` 三种坏法（禁掉迁移文件 / 改索引表达式丢 `COLLATE NOCASE` /
   改 `SORTS["name"]` 丢 `COLLATE NOCASE`）全部 RED，控制组 GREEN，字节级还原。证明守卫抓得住
   「索引名在但表达式不对」与「排序口径与索引脱钩」两类复发。

**被否的两种**：① 加 `ANALYZE` —— 实测无收益，且违反「慢操作只许放在显式慢路径」；
② 用 `LOWER(name)` 代替 `name COLLATE NOCASE` —— 与产品排序口径脱钩，守卫会 RED（第 3 条）。

**代价**：写入侧 +7.4%（每份文档多一次 B-tree 更新）；库体积 +索引大小（8 万份约 2.5 MB，
占库总体积 8%）。**不解决虚拟化那一半**：浏览走索引，搜索走 FTS，两件事分开算（**ISSUES I51**
那条是另一条路）。

## D-061 · 语义向量写路径只按显式点名触发（2026-10-19，**ISSUES I63** 丙 + 丁）

**背景**：阶段 6 的语义层此前只有读路径 —— `VectorStore.add/add_batch/delete_by_doc` 零产品调用方、
`vector_status` 恒为默认 `na`、`jobs.KINDS` 里的 `"vector"` 从不入队。ISSUES I63 丙/丁 要补的就是这唯一
缺失的一环：**让 `VectorStore` 有真调用方、`vector_status` 真有人推进、`"vector"` 真能进 worker**。
补的时候撞到一个必须定死的岔路：向量该在什么时候建。一条 embedding 任务对一份 946 页的文件就是
946 次模型前向（真语料里 946 页的部件实测存在），"扫一遍全库把所有已索引正文的都悄悄排上向量"看着
省事，实际是把 GPU 时间烧在用户没要求的文件上。

**决定**（四条，每条都可断言）：

1. **唯一入口 = 用户点名（`request_vectors(doc_ids)`），不做全库自动建**：沿用 OCR 阶段 5 的
   Q3=甲 口径，与 D-006「不扫全库自动跑重活」一致。`VectorService` 里没有"遍历全库把 pending 都
   排上"的方法 —— 想建向量就得给出具体 doc_id 集合。这一条把"什么时候愿意为语义搜索付 GPU 钱"
   的决定权交回用户，而不是服务层替他决定。
2. **入场券是一份可搜的正文（`text_status ∈ TEXT_SEARCHABLE`）**：没正文就没东西可嵌，对从没索引
   过的文档直接建向量只会得到一堆空页向量污染语义搜索。`_why_skipped`（进队前）与 `build_vectors`
   （执行时）两处都判，前者挡在门外给回执、后者拒已入队的漏网者；空正文页（`char_count=0`）逐页跳过。
3. **重嵌前先 `delete_by_doc` 清旧向量**：这是 `VectorStore.delete_by_doc` 在产品里的调用方。
   页变少时旧向量的孤儿只有清旧能带走（`add_batch` 的 `(doc_id,page_no)` 去重只覆盖同名页、带不走
   少掉的那页），不清则语义搜索命中一个已经没有正文的页。测试对应用意选"页变少"场景做断言，
   正是因为同页集合重嵌删不删 `delete_by_doc` 都不翻倍、照不出这条（本轮实测证伪）。
4. **失败一律留 `failed` + 原文，可取消留 `stale`，绝不伪装 `done`**：模型没装（`FileNotFoundError`，
   本机 `%LOCALAPPDATA%\PdfArchiver\models` 今天就不存在）当场写 `failed` 并把原文进 `last_error`
   （AGENTS.md 不许伪装成功）；逐页问 `monitor.cancelled()`，中途停下写 `stale` 并抛 `JobCancelled`，
   "跑了半截"不算"跑完"。`vector_status` 的推进由 `documents.set_vector_status` 独占，处理函数拿不到
   仓储、写不出表里没有的流转。

**被否的两种**：① 把向量自动接进索引链路（索引完就排队建向量）—— 违反 D-006/Q3=甲 的"用户点名"，
会为没被要求的文件烧 GPU；② 全库 `pending` 扫描入口 —— 同①，且 202 万页量级下是自我 DoS。
真要"一键全库建向量"，那是需要单独线框 + 预算闸门的界面决定，不在本条范围。

**代价**：语义搜索/AI 分类在真界面上**仍要等一个"建向量"入口**才会出结果 —— 本轮接通的是服务层
写路径与 worker 调度，`ui/` 下没有按钮调 `request_vectors`（AGENTS.md：线框未逐屏确认前不写界面代码）。
所以 `vector_status` 在只走 GUI 的用户机上仍停在 `na`，直到该入口落地或手工 enqueue。测试夹具

不是模型本身（模型在场性由 ISSUES I37 的路径守卫与 ISSUES I84 的失败可见另行覆盖）。

**追注 · 2026-10-28（第 2 条入场券被 **ISSUES I116** 甲 改写）**：本条原第 2 条写的是
「入场券是一份可搜的正文（`text_status ∈ TEXT_SEARCHABLE`）」。轮三十二在真库上撞到：OCR 出来的正文
