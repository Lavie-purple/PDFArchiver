# S1 · 主窗口 —— 库视图 + 搜索结果面板（同屏）

## 它必须承接的六件事（不是审美，是实测逼出来的）

| 必须做 | 来源 | 不做的后果 |
| --- | --- | --- |
| 列表虚拟化，一次只渲染视口内那些行 | p0/p2：**7,768 份**、单目录最多 **722 份**、×10 档 **8 万份** | 全量灌进 `QListWidget` 在千行级就卡死（AGENTS.md 明令禁止） |
| 命中结果与文档列表**同屏可对照** | 阶段 3 需求：命中要能定位到**页码** | 分两屏来回跳，"边看命中边归类"这个主动作就没了 |
| 短查询要显示"正在用慢速匹配"并限制结果数 | p1：**<3 字 trigram 命中不了**，LIKE 回退实测 2 字 **499ms** / 单字 **424ms** | `G2 ≤ 500ms` 被无感触发，而且用户以为卡住了 |
| OCR 命中与语义命中**来源可辨**，不许渲染成原文 | 库里 `source_kind` 已分开，实测标签「OCR 识别（可能有错字）」；ROADMAP:187 | 把模型/识别文本当原文展示 = SPEC 五「不许凭空编造」正违规 |
| 一条常驻的后台任务状态（队列 / 谁在占 GPU / OCR 今日预算 / 索引体积） | p5：**GPU 只能串行**（空闲 1369MiB，OCR 一次吃 701MiB→668MiB）、D-028 的**今日页预算跑满即停**、docs/RISKS 2.9：索引 **28–48GB** | "队列无故少了一批""什么都没发生"——就是台账 **I23** 在说的事 |
| 双击行后**先出元数据再按需渲染正文** | p2：最大 **946 页 / 1.1GB** 单文件、`open_ms` 最差 **232.7ms**；p3：单页渲染中位 **135.1ms** | 打开一本大书就把整个界面冻住 |

**1024×720 的降级（必须写进断言，不是"到时候看"）**

```
算术：左树 236 + 中列表 ≥480 + 命中面板 ≥360 = ≥1076 > 1024  →  三栏放不下，必须牺牲一栏。
取舍：**命中面板改为浮层**（点搜索框或按快捷键时覆盖在列表右侧 420px，可关），
      左树收成 **图标条 48px**，中列表吃掉剩下的 ~940px。
理由：搜索是"要结果时才需要看结果"的动作，而分类树是"随时要知道我在库的哪个位置"的动作 ——
      牺牲前者比牺牲后者便宜。
```

## 区域 → 数据来源 → 可断言的硬条件

| 区域 | 数据从哪来（现成的类/字段，不新造口径） | 断言点（能写成测试才算数） |
| --- | --- | --- |
| 搜索输入 + 字段多选 | `search.service.SearchService.search(Criteria)`；`Criteria.in_fields` 用 `FIELD_FILENAME/PATH/METADATA/BODY` | 一次查询的 SQL `LIMIT ≤ 200`（`MAX_PAGE_SIZE`）；四通道各自 `CHANNEL_LIMIT = 200` |
| 短查询提示 | `SearchResult.channel`（`fts` / `like_fallback`）；`indexing/fts.channel_for()` | `channel == "like_fallback"` 时**必须**显示提示行；`fts` 时必须**不**显示（两向都测） |
| 结果计数与截断 | `SearchResult.matching_documents` / `counts_by_field` / `truncated_fields` | 面板顶部显示的数**只能**来自这三个字段；出现自算的 `len(...)` 判红 |
| 命中行（页码 + 片段 + 来源） | `Hit(doc, field, snippet, page_no, score, body_source)` + `Hit.field_label` / `Hit.source_label` / `Hit.highlight` | 每条命中必须渲染出 `page_no`；`page_no is None` 的行**不许**显示"第 ? 页"，改为显示通道名 |
| 语义命中的标注 | 阶段 6 的 `SearchResult` 扩展（尚未存在） | **未装模型时这一栏必须完全不存在**（不是灰掉、不是空表），否则就违反 SPEC:166「语义是独立模块」 |
| 分类树（甲的左下） | `db/repositories/categories`（已有增/查/树/link；改名调层级删除合并属阶段 3） | 树节点数 = 仓储返回数；节点**不许**显示"该分类下 N 篇"除非那个数是从仓储现数的（阶段 3 要加逐节点计数） |
| 文档列表 | `DocumentRepository` + `DocFilter` / `where_for_filter` | 渲染行数 ≤ 视口行数 + 缓冲（虚拟化）；默认排序与 `Criteria.sort` 一致，翻页不重不漏 |
| 筛选 chips（乙的顶栏） | `Criteria` 的 `category_ids / tag_ids / tag_match_all / modified_from,to / root_key / fts_status / min_pages / min_size_bytes / missing_only` | chips 序列化后必须能 `== ` 回同一个 `Criteria`（这是"智能集合"的 `query_json` 的同一份东西，不写第二个格式） |
| 存为智能集合 | `collections` 表（`0001_initial.py:126`：`id, name, query_json, note`） | 存进去→重开→条件与结果一致；删集合**不许**动文档（SPEC 3.3.5：只存查询条件，不复制文件） |
| 底栏后台状态 | `services/patrol` + `jobs` 队列 + `ocr_service` 的预算读数 + `TextRepository.stats()` | **不许**出现"整库 OCR 总进度百分比"（§五 明令：那必然是假数字）；只能显示"本次点名 N 份里第 k/n 页" |
| 索引体积 / 磁盘剩余 | `stats()` + `shutil.disk_usage` | 显示的数与 `docs/RISKS 2.9` 同一口径（字节换算规则唯一） |
| 监听异常 | 巡检与 watcher 状态（阶段 2 已有"根目录不存在时不判缺失也不崩"的断言） | 异常根必须给**原因文本**，不许只给一个红点 |

## 两案的取舍（说人话版）

| | 甲 · 三栏常驻 | 乙 · 一栏到底 |
| --- | --- | --- |
| 主动作 | "边看命中边归类"——树和命中都常驻 | "以文档为主、命中为注"——一屏一件事 |
| 虚拟化代价 | **低**：行高统一，`QTableView` 的行号↔坐标换算是 O(1) | **高**：行高随展开变化，要么关掉按需取行改为整表测高（在 8 万行档就是 O(n²)，AGENTS.md 明令禁止），要么限制"同时展开数"并为此加一条断言 |
| 1024 最小档 | 必须牺牲命中面板（改浮层）+ 树收图标条 | 天然适配 |
| 拖拽归类（选中→拖进分类） | **成立**，树常驻 | 不成立，得走"移入分类…"对话框 |
| 命中很多条时 | 面板自己滚，列表不动 | 列表里插满命中行，位置感变差 |
| 开发顺序 | S1 一次到位 | S1 简单，但"同时展开数"这类限制要另写规则 |

**我的推荐：甲 + 1024 下降级成"命中面板浮层 + 树收图标条"。**
决定性理由是虚拟化那一行：乙的变行高会把 O(1) 的行号换算打回 O(n)，
而这正是 AGENTS.md「禁止全量渲染 / 禁止 O(n²)」在项目里唯一会**被 UI 自己犯掉**的地方
（阶段 0–5 的禁令都在后端和文档里，没碰过列表控件）。
