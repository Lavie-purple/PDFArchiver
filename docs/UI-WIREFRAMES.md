## 两案的取舍

| | 甲 · 批次为主 | 乙 · 流水为主 |
| --- | --- | --- |
| 与数据模型的关系 | **同构**：`file_operations` 就是台账单位，`undo_of` 也是批级外键 | 以项为主体，撤销要跨批次收集 → "部分撤销的批次"这个态**表里没有** |
| 崩溃后第一眼看到什么 | 哪个批次没走完 + 需要判断的项 | 一串时间线，得自己找出没走完的那批 |

| 撤销的可解释性 | 高（"撤销 #128"一句话讲完） | 低（"撤销所选 12 项，来自 #128 与 #126"要先教什么是"所选"） |

| 虚拟化 | 两处（批次列表、详情逐项表），都按现成索引分页 | 一处（流水），但它没有可走索引的默认排序 |

**我的推荐：甲 · 批次为主 + 「需要判断的项」常驻顶部。**
决定性理由不是审美，是**表结构**：`undo_of` 是批级外键，撤销的单位天生是批次；乙 的勾选式撤销要么改表、
要么在界面里造一个库里不存在的"部分撤销"态 —— 那是本项目为多口径付账最多的那一类错（**ISSUES I28 / ISSUES I31 / ISSUES I37 / ISSUES I40**）。

## 区域 → 数据来源 → 可断言的硬条件

| 区域 | 数据从哪来（现成的，不新造） | 断言点 |
| --- | --- | --- |
| 计划表逐行 | `file_operations.plan_json`（一批次一个计划）+ `operation_items(src_path, dst_path, kind, state, reversible, error, src_sha256, dst_sha256)` | 表行数 **== `items_total`**；出现界面自己拼路径算出来的行判红（目标路径只能来自 plan） |

## 两案的取舍

| | 甲 · 全量表常驻 | 乙 · 三段向导 |
| --- | --- | --- |

## 两案的取舍

| | 甲 · 连续滚动 | 乙 · 单页翻页 |
| --- | --- | --- |
| 命中跳转后的位置感 | 好（还在同一文档流里，上下都有上下文） | 断（只有当前页） |
| 渲染压力 | **高**：135.1ms/页 vs 滚轮速度，必然跑输 → 必须定"滚动中不排队渲染，停下才渲染"这条策略 | **低**：一次一页，翻页即渲染，最坏值可预期 |
| 946 页 / 1.1GB 大文档 | 虚拟化上限 ≤5 页位图驻留，否则顶穿 `G8`（RSS ≤1.2GB） | 天然只有 1 页驻留 |

| 双页并排（书册感） | 别扭 | 自然 |
| 实现与测试面 | 要测"滚动跑输渲染"的降级路径 | 少一条路径 |

**我的推荐：甲（连续滚动）+ 上限 5 页驻留 + "滚动中不排队、停下才渲染"。**
理由：这一屏的主角是**"从命中跳过来读那一段"**，连续流让命中处上下有上下文；
翻页式在"跳页—读—再跳页"的循环里每次都是白屏起步。渲染跑输滚轮这件事不是靠加阈值解决，
是靠**取消滚动中的渲染排队**这条策略解决，它是可断言的（测：连续滚轮事件期间渲染调用数 = 0）。
