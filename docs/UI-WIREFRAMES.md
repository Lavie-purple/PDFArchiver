## 区域 → 数据来源 → 可断言的硬条件

| 区域 | 数据从哪来（0001 的列，不新造） | 断言点（能写成测试才算数） |
| --- | --- | --- |
| 批次列表 | `file_operations` 按 `created_at DESC` 分页（阶段 4 待建的 `OperationRepository`） | 列表行数 = 分页取回的条数；`undo_of` 那条**不许**折叠成原批次的子行（两条独立事实） |
| 计数条 | `items_total / items_done / items_failed` | 三个数只能来自这三列；出现自算的 `len(...)` 判红；"未做"必须是三者派生 |
| 批次耗时 | `finished_at - started_at` | 任一为 `NULL` 时**必须显示"未完成 / 未知"**，不许显示 `0s` 或负数（与 D-028 的"剩余夹到零"同族） |
| 逐项表 | `operation_items` 按 `(op_id, state)` 分页（正好走 `ix_items_op_state`） | 渲染行数 ≤ 视口行数 + 缓冲；`error` 列显示**原文**且可复制，不许只翻译成一个图标 |
| 逐项态 vs journal | `operation_items.state` ↔ journal 态 | 读到 `dst_verified` 之前不许显示"已移动"；**两词表的映射口径必须先由 ISSUES I42 定下来**，否则这条断言写不出来 |
| 需要判断的项 | 恢复矩阵产出的 `orphan_dst` / `lost` 标记 | `orphan_dst` 分组里**不许有任何"删除"动作是默认按下**的；`lost` 只上报不给恢复按钮 |
| 未知状态分组 | 恢复矩阵归类结果（**G17**） | 为空时也要渲染"未知状态 0"这一行；不为空时每条都能跳到 journal 原文行 |
| 撤销动作 | 新批次：`kind='undo'`、`undo_of=128`，项取 `reversible=1` | 撤销批次与原批次在台账里是**两条**；`reversible=0` 的项出现在撤销计划里即判红 |
| 撤销后读数 | **G18** 四件：源存在 / 字节数 / sha256 / 目标消失 | 四件逐项显示，缺任何一件不许把批次标成"完成" |
| 分级确认控件 | 与 §S3 定案**同一条规则**（唯一存放处） | 同一批含不可逆项却只弹复选框 → 判红；S6 的恢复若另造控件 → 判红 |

## 两案的取舍

| | 甲 · 批次为主 | 乙 · 流水为主 |

## 两案的取舍

| | 甲 · 连续滚动 | 乙 · 单页翻页 |
| --- | --- | --- |
| 命中跳转后的位置感 | 好（还在同一文档流里，上下都有上下文） | 断（只有当前页） |
| 渲染压力 | **高**：135.1ms/页 vs 滚轮速度，必然跑输 → 必须定"滚动中不排队渲染，停下才渲染"这条策略 | **低**：一次一页，翻页即渲染，最坏值可预期 |
| 946 页 / 1.1GB 大文档 | 虚拟化上限 ≤5 页位图驻留，否则顶穿 `G8`（RSS ≤1.2GB） | 天然只有 1 页驻留 |
| 键盘党 | 方向键滚页 | `PgUp/PgDn` 直读，无歧义 |
| 双页并排（书册感） | 别扭 | 自然 |
| 实现与测试面 | 要测"滚动跑输渲染"的降级路径 | 少一条路径 |

**我的推荐：甲（连续滚动）+ 上限 5 页驻留 + "滚动中不排队、停下才渲染"。**
理由：这一屏的主角是**"从命中跳过来读那一段"**，连续流让命中处上下有上下文；
翻页式在"跳页—读—再跳页"的循环里每次都是白屏起步。渲染跑输滚轮这件事不是靠加阈值解决，
是靠**取消滚动中的渲染排队**这条策略解决，它是可断言的（测：连续滚轮事件期间渲染调用数 = 0）。

| 分类树（甲的左下） | `db/repositories/categories`（已有增/查/树/link；改名调层级删除合并属阶段 3） | 树节点数 = 仓储返回数；节点**不许**显示"该分类下 N 篇"除非那个数是从仓储现数的（阶段 3 要加逐节点计数） |
| 文档列表 | `DocumentRepository` + `DocFilter` / `where_for_filter` | 渲染行数 ≤ 视口行数 + 缓冲（虚拟化）；默认排序与 `Criteria.sort` 一致，翻页不重不漏 |
| 筛选 chips（乙的顶栏） | `Criteria` 的 `category_ids / tag_ids / tag_match_all / modified_from,to / root_key / fts_status / min_pages / min_size_bytes / missing_only` | chips 序列化后必须能 `== ` 回同一个 `Criteria`（这是"智能集合"的 `query_json` 的同一份东西，不写第二个格式） |
| 存为智能集合 | `collections` 表（`0001_initial.py:126`：`id, name, query_json, note`） | 存进去→重开→条件与结果一致；删集合**不许**动文档（SPEC 3.3.5：只存查询条件，不复制文件） |
| 底栏后台状态 | `services/patrol` + `jobs` 队列 + `ocr_service` 的预算读数 + `TextRepository.stats()` | **不许**出现"整库 OCR 总进度百分比"（§五 明令：那必然是假数字）；只能显示"本次点名 N 份里第 k/n 页" |
| 索引体积 / 磁盘剩余 | `stats()` + `shutil.disk_usage` | 显示的数与 `docs/RISKS 2.9` 同一口径（字节换算规则唯一） |
| 监听异常 | 巡检与 watcher 状态（阶段 2 已有"根目录不存在时不判缺失也不崩"的断言） | 异常根必须给**原因文本**，不许只给一个红点 |

## 两案的取舍（说人话版）

| | 甲 · 三栏常驻 | 乙 · 一栏到底 |
| --- | --- | --- |
| 主动作 | "边看命中边归类"——树和命中都常驻 | "以文档为主、命中为注"——一屏一件事 |
| 虚拟化代价 | **低**：行高统一，`QTableView` 的行号↔坐标换算是 O(1) | **高**：行高随展开变化，要么关掉按需取行改为整表测高（在 8 万行档就是 O(n²)，AGENTS.md 明令禁止），要么限制"同时展开数"并为此加一条断言 |
| 1024 最小档 | 必须牺牲命中面板（改浮层）+ 树收图标条 | 天然适配 |
| 拖拽归类（选中→拖进分类） | **成立**，树常驻 | 不成立，得走"移入分类…"对话框 |
| 命中很多条时 | 面板自己滚，列表不动 | 列表里插满命中行，位置感变差 |
| 开发顺序 | S1 一次到位 | S1 简单，但"同时展开数"这类限制要另写规则 |

**我的推荐：甲 + 1024 下降级成"命中面板浮层 + 树收图标条"。**
决定性理由是虚拟化那一行：乙的变行高会把 O(1) 的行号换算打回 O(n)，
而这正是 AGENTS.md「禁止全量渲染 / 禁止 O(n²)」在项目里唯一会**被 UI 自己犯掉**的地方
（阶段 0–5 的禁令都在后端和文档里，没碰过列表控件）。
