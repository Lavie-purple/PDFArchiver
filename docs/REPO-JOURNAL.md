AGENTS.md 元规则要求的入职手册件之一：记录**仓库结构、命名规则、忽略规则**的变更，

## R-001 · 2026-10-14 · 文档从数字编号改成规范文件名

**改前**：`docs/00-阶段0验证结论.md` … `docs/08-阶段0交付报告.md`（数字前缀只为排序）。
**改后**：按用途命名 —— `VERIFICATION / ARCHITECTURE / DATABASE / ROADMAP / TESTING / DECISIONS / CHANGELOG`，
加支撑件 `RISKS / UI-SCREENS / ISSUES / stage-reports/`。
**原因**：用户指定的工程文档口径就是这套名字；数字编号会让"文档属于第几阶段"和"文档是什么"混成两个口径，
阶段推进后编号顺序就乱了（`00` 已经出现两次改序）。
**连带处理**：全部交叉引用一次改写（15 个文件，含 `requirements/*.txt`、探针 docstring、守卫 docstring），
改完 `grep -rn "docs/0[0-8]"` 为空；用 `git mv` 保留历史。

**规则**：AGENTS.md 把「需求契约 / 工时埋点 / AI 记忆文件」列在本机工作文件区，仓库根只该有 `README.md` 与产品代码。
**动作**：`.gitignore` 追加 `PROJECT_SPEC.md`（原条目 `SPEC.md` 匹配不到这个文件名）。

不需要改任何文档内容。这条是**可逆的结构决定，不是技术结论**。

## R-006 · 2026-10-14 · 阶段 1 落地时的三类"验证物"分界

填代码时同时冒出三种"跑一下看对不对"的东西，不划清界线就会互相抄、互相冒充。本项目的分界：

| 种类 | 位置 | 特点 | 什么时候跑 |
| --- | --- | --- | --- |
| 探针 | `tests/probes/pN_<主题>.py` | 验证**技术前提**（依赖、平台、量级），一次性、可重跑、产物写 `.probe_work/`、末尾 `VERDICT` | 换机器/换依赖/怀疑环境 |
| 守卫 | `tests/guards/test_<规则>.py` | 验证**结构规则**（依赖方向、SQL 位置、依赖版本、迁移不丢数据），常驻、每次改动都跑 | 每次改动 + 门禁链 |
| 断言自证 | `tests/probes/p9_reverse_injection.py` | 不验产品，验**测试自己有没有牙齿**：把坏法注进临时副本，要求对应测试必红 | 每阶段收尾（已进门禁链） |

守卫和断言自证的区别就是：守卫红 = 代码违反了规则；p9 红 = 规则写在测试里但**抓不住违反**。
两者都进 `gates/stage1.py`，末行统一 `VERDICT: ALL GREEN`。

## R-008 · 2026-10-15 · 阶段 5 收尾：占位销账、OCR 层落位、两本样本书改成代号

**1）`.gitkeep` 按 R-004 的约定销账。** 阶段 1 留了 8 个占位并写明"某层开始有真代码就删掉它"。

**3）新增两份入库文档 + 一条门禁。** `docs/OCR.md`（用户视角：装 / 配置 / 怎么用 / 故障处理）；
`docs/stage-reports/阶段5-交付报告.md`。门禁沿用 R-007 的"每阶段一个"：`gates/stage5.py`，
全链实测 382s（约 6.5 分钟），`--quick` / `--no-injection` 约 141s。

旧口径（x = 连续交付到第几阶段）在这里会自相矛盾。`docs/CHANGELOG.md` 头部已改写口径并写明跳号原因，

## R-009 · 2026-10-15 · 最终交付轮新增的两件东西与五条放置规则

**1）`gates/final.py` 与 `gates/stageN.py` 的分工（新文件放哪，照这张表判）。**

| 脚本 | 负责什么 | 不许做什么 |
| --- | --- | --- |
| `gates/stageN.py` | **一个阶段**的准出判据，阈值只在该脚本里出现一处 | 不许把别的阶段的判据搬进来 |
| `gates/final.py` | **交付编排**：分段调用上面那些脚本 / 探针里**已存在**的断言 | 不许新增判定口径、不许写死任何性能数字（V19）；改判据要回各阶段脚本改 |
| `packaging/build.py` | 构建 + **产物内容断言**（模型 / DLL / `.dist-info` / 迁移 `.py` / 体积对账） | 不许把构建成功当交付成功 —— 内容缺一项就红 |
| `packaging/frozen_smoke.py` | 在**仓库外的临时目录**跑真产物（首启 / 扫描 / 检索 / OCR / 重启 / 强杀恢复 / 无本机路径） | 不许在仓库内跑产物，否则"复制出去还能跑"这句没被验过 |

放 `packaging/` 而不是 `gates/`：这两个文件的主题是**产物**，`gates/` 只放"准出判据"。
新增同类文件时按主题选目录，不要往 `gates/` 里堆。

**2）探针不许自写产品的动作（I33 的规则化）。** 探针若声称在测"产品的某个入口函数"，
就必须 **import 并调用那个入口**，再把入口自己报的数与探针独立数出来的数**双向对账**。
本轮实测的代价：p14 的 ⑤ 因为在探针里自己写了一遍 `VALUES('rebuild')`，
把产品的 `rebuild_all()` 摘掉之后它照样 9/9 全绿 —— 一条恒绿的断言比没有断言更糟，
因为它会让交付文档里那句"rebuild 是真补救"看起来有出处。同类问题一次性处理：
新增 `tests/integration/test_probe_sql_sensors.py`（静态核对 SQL 表名 + 等式对齐产品口径），
今后任何工具读产品库都必须被这类守卫钉住，而不是逐个 bug 打补丁。

**3）`.probe_work/` 里的东西不能当引用目标。** 它是 gitignored 且**收尾清零**的现场目录，
所以"出处见 `.probe_work/scratch_*.py`"这种引用会在收尾那一刻变成空指。
本轮把三处这类引用改指长期存在的东西（p14 常驻探针、台账 I29），规则写进 `docs/README.md` 维护约定第 7 条。
**同一批还测出一件更麻烦的**：`I<n>` 这个字形在本项目同时是台账编号、p9 坏法编号与 p10 坏法编号
（`docs/ISSUES.md` 的行号｜`docs/TESTING.md` 四 I1–I46｜`p10_reverse_injection_ocr.py` 代码里是裸数字），
509 处引用里 **453 处是裸写**（38 处写了"注入"、18 处写了"ISSUES"）。本轮**只声明规则、不改写存量**（新写入一律
`ISSUES I<n>` / `p9 注入 I<n>` / `p10 注入 #<n>`），规模与销账条件记在 **I35**。

**4）交付文档的四份 + 五分栏是断言的字段名。** `gates/final.py` 的 `gate_docs()` 里写死了
`USER_DOCS`（INSTALL / USAGE / BACKUP-RESTORE / TROUBLESHOOTING）与 `FIVE_COLUMNS`
（已实现且已通过测试 / 已实现但尚未充分验证 / 部分实现 / 尚未实现 / 已知问题及其影响）。
**这些串改名要连门禁一起改**：它们是"交付诚实性"的机器判据，文件名或栏名一改，判定就静默失效。
占位符判据是 `TBD|TODO|待填|<<…>>|此处省略`，命中即红 —— 所以写文档时不能留"回头再填"的字面串，
要写就写实测结果，没测就写"未实测"并在台账里挂着。

**5）门禁输出里"N 条全绿"的 N 只许数真能变红的行。** `gates/*.py` 里一条 `Row` 就是一个计数单位，
所以"这次没测、但先给个 PASS 并写明未跑"这种写法会把计数变成谎话 ——
`gates/final.py` 的"一致性核查 p12 对真实数据根"正是这个形状（**ISSUES I36**，OPEN）。
规则一次性声明：**没跑的东西用普通打印或 `SKIP` 表达（不进 `checks`），或者干脆算 RED**；
"措辞诚实"不能替代"计数诚实"。同类的另两处已按这条做对了：`--only` 跳过的段只打印不计数、
`gates/stage5.py` 没有占位行。

## R-005 · 命名与放置规则（供后续新增文件时对照）

| 类型 | 放哪 | 命名 |
| --- | --- | --- |
| 实测证据 | `docs/VERIFICATION.md` 正文 + `.probe_work/*.json`（不入库） | 探针 `pN_<主题>.py`，产物同名 `.json` |
| 决策 | `docs/DECISIONS.md` 追加一条 `D-0NN` | 一条一段，含被否方案 |

| 阶段结论 | `docs/stage-reports/阶段N-交付报告.md` | 一份一阶段，写完不改历史，只追加"更正" |
